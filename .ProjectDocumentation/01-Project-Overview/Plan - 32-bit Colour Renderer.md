# Plan - The 32-bit Colour Renderer

**Decided:** 2026-09-07. **Branch:** `renderer-32bit` (local; backup tag `v1.10.017-pre-renderer` on GitHub is the last 8-bit build). **Versions:** 1.11.001 and up.

## Why

The game drew everything into an 8-bit buffer: every pixel was an index into one 256-colour palette, chosen per dungeon type. All art, all text colours and all monster recolours had to share those 256 entries, of which about 128 are free once the level's own tiles are counted. That is what made new art muddy, capped text at .trn remaps of the font, and limited unique-monster tints to shuffles of the level palette. The upgrade replaces the index buffer with a true-colour one, so a palette becomes a per-asset convenience instead of a game-wide limit.

## The stages

### Stage 1 - the 32-bit buffer (DONE, v1.11.001 to 1.11.003)

The screen surface is XRGB8888. Every draw kernel (sprites, tiles, fills, lines, text) resolves a palette index to its RGB value at write time through `PaletteRGB`, rebuilt whenever the palette changes. Fades and the red damage flash became present-time transforms. Offscreen 8-bit surfaces are unchanged.

- Rule: pixel-identical to the 8-bit build. The golden tests enforce it; the user confirmed in play ("99.9% same").
- First-look fixes: the palette table rebuilt at once in LoadPalette (loading screens, first frames), raw index writes routed through SetPixel, index fills replaced by FillRect.
- First true-colour art: the loading screens, decoded from the original CEL through its palette at load and scaled to screen height, and the user's 16:9 paintings from the private archive.

### Stage 2 - per-asset palettes (NEXT)

Each piece of the fork's own art carries its own 256-colour palette, generated by quantising its PNG at build time, and is resolved through that palette at draw time instead of the level's. Original Blizzard art keeps the level palette and is untouched. Lighting, which today is a palette-index lookup per light level, becomes an arithmetic darkening of the RGB value for these assets.

- What it buys: new art (HUD, panels, canvases, monsters, items) shows its own colours in every dungeon, with no fitting to the level palette and no colour theft between assets.
- Unique-monster recolours become free: a tint is a palette of the monster's own, not a remap inside the shared 128 entries.
- Cost: a palette per asset in the MPQ (768 bytes each), the pack tool quantises, the sprite loader learns to attach a palette to a CLX, and the lighting kernels get an RGB path.
- Gate: golden tests stay green for every asset that keeps the level palette; a new golden per converted asset.

### Stage 3 - RGB text (after stage 2)

A text colour becomes an RGB value instead of a .trn remap of the font sprite. The font glyphs are drawn through a colour, not a translation table. The .trn machinery stays for the original fonts and for anything that still wants a palette look.

- What it buys: any colour for any text, no file per colour, no "borrowing", no ramp/pass arithmetic. The 12-bit colour field in UiFlags stays as the index into a colour table that now holds RGB values.
- Consequence for the Font Colour Legend: it stops being a menu of what the palette allows (ramps and passes) and becomes a registry of the colours the game actually uses: ID, hex value, where it appears. Shades are then chosen by eye, not by palette pass. (User, 2026-09-07: "the legend now only needs to include colors we actually use.")
- Gate: every existing legend colour reproduces its current RGB exactly, so nothing in play changes on the day it lands; new colours come after.

### Stage 4 - cleanup (optional, later)

Retire the 8-bit offscreen surfaces where nothing needs them, drop the per-colour .trn files for the fork's own fonts, and regenerate the legend and wiki from the colour table.

## Order and gates

1. Stage 1 in play, verified. Done.
2. Stage 2, one asset class at a time (HUD first, then panels, then monsters), a build and a screenshot per class.
3. Stage 3, with the legend rebuilt as its last step.
4. Push to GitHub only when the user asks; the RTM folder tracks the newest build.
