# Audit 5: interface ownership, closing and drawing

Baseline: v1.12.188, commit `acc970335a9c0ecd5287f236fb601f2c8d7a8601`, 2026-09-26.

## UI-01 [P3]: Escape does not close the workshop independently

Confidence: **confirmed**. Evidence: executed `PressEscKey` probe and source tracing.

Locations: `Source/diablo.cpp:3840` places `CloseWorkshop()` inside the `IsStonegateMenuOpen()` branch. `Source/control.cpp:328` defines the ordinary right-panel ownership as inventory/spellbook; workshop closure is not supplied by those flags. `Source/diablo.cpp:1059` handles Escape's fall-through to the menu.

Trigger: open the Mystic workshop, close other panels, leave the Stonegate menu closed, and press Escape. `PressEscKey` never calls its workshop closer. The production probe with a 1280×720 layout leaves `IsWorkshopOpen()` true. Depending on other open panels, Escape instead closes another panel or opens the pause menu. This also makes the exit path in SAVE-01 reachable while the bench retains custody.

Suggested fix: handle an open workshop in an independent Escape branch, consume the key, and honor `CloseWorkshop` refusing to close while it holds items with no destination. Do not move the call into a branch that depends on an unrelated panel.

Failing regression: retained `WorkshopEscapeClosesTheVisibleWindow`. Add variants with inventory open/closed, other floating windows, empty bench and full-storage refusal; assert only the intended window is affected and no staged item is lost.

## UI-02 [P2]: the workshop is missing from the shared world-click rejection predicate

Confidence: **confirmed** for the geometry/dispatch defect. Evidence: executed production interface predicate and traced right-click fall-through; no actual movement/cast was injected into a running game.

Locations:

- `Source/control.cpp:304`: `IsOverAnyInterface` does not include workshop ownership.
- `Source/oracool/hud_layout.cpp:482`: its floating-window delegate lists Cube/recipe/runeword/skill-picker/event-log surfaces, but not the workshop.
- `Source/oracool/workshop.cpp:1509`: authoritative `IsPointOverWorkshop` already exists, including workshop tabs.
- `Source/diablo.cpp:970`: right-click rejects world actions using `IsOverAnyInterface`, then dispatches the readied spell/basic action.
- `Source/diablo.cpp:563`: left-click has a separate workshop handler; that does not protect right-click.

### Trigger and consequence

With the workshop open and overlapping panels closed, right-click inside workshop content or its tabs. The shared UI predicate reports that the point is outside the interface even though `IsPointOverWorkshop` returns true. With no other earlier handler consuming the click, right-click can reach world movement/spell dispatch beneath the workshop. In town an empty right button takes the basic-action path that can walk; the exact resulting action depends on cursor/readied state.

The retained probe opens the Mystic at 1280×720 and tests a point 230 pixels right and 170 pixels down from its page origin. Workshop hit testing succeeds; `IsOverAnyInterface` returns false. This is an executed disagreement between production predicates, not a screenshot-based inference.

### Suggested fix and failing regression

Register the workshop's authoritative hit test in the common interface predicate. Review world-cursor and quick-cast dispatch consumers so they use the same ownership rule, rather than adding another duplicated rectangle.

`WorkshopCountsAsInterfaceForWorldRejection` fails today. Extend across hosts/tabs and supported resolutions, with edge/outside points, and instrument dispatched commands to assert no world command is sent for either mouse button over workshop surfaces.
