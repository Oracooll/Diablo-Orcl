# Audit 1: saves and state that outlives a game

Baseline: v1.12.188, branch `renderer-32bit`, commit `acc970335a9c0ecd5287f236fb601f2c8d7a8601`, 2026-09-26. All source references below are at this commit. Source root: `C:\Users\hroga\OneDrive\2. Personal Files\Software\Diablo\Diablo Orcl`.

## SAVE-01 [P1]: workshop custody is absent from saving and game teardown

Confidence: **confirmed by code tracing** for the missing custody/reset integration and resulting exit-save omission. Evidence: source inspection, not an executed save/reload or gameplay reproduction. The attempted isolated bench-return fixture is inconclusive and excluded from evidence.

Locations:

- `Source/oracool/workshop.cpp:440`: process-wide workshop state; `:443`: bench storage.
- `Source/oracool/workshop.cpp:2667`: depositing an item moves it from `HoldItem` into `Bench` and clears the held item.
- `Source/oracool/workshop.cpp:1024`: returning the bench transfers its item to the current `MyPlayer`.
- `Source/oracool/workshop.cpp:1463`: close returns bench and craft-grid contents, but can refuse when storage is full.
- `Source/oracool/workshop.cpp:1521`: `ResetWorkshopForNewGame` clears the bench, craft grid, counters and open state. There are **no production callers**; the other references are its declaration and comments.
- `Source/oracool/auto_save.cpp:74`: `IsSafeToSave` excludes the unsaved Levski grid but not the workshop.
- `Source/oracool/auto_save.cpp:265`: `SaveOnExit` returns cursor-held items, then saves hero/stash; it does not recover the workshop containers.
- `Source/gamemenu.cpp:148`: exit closes Levski before saving, but not the workshop.
- `Source/diablo.cpp:226`: `FreeGame` resets other mod state, but does not reset the workshop.

### Trigger and consequence

Move a uniquely identifiable owned item onto the Mystic bench or workshop craft grid. Leave it there, close the inventory if necessary, and use Escape to reach the game menu (UI-01 explains that route). Exit the application. The item is no longer in the saved inventory, belt, equipment, stash or cursor; workshop custody is not serialized or returned by this path. Restarting the process discards that custody and loses the item. A periodic character save while the workshop holds the item likewise writes a state that omits it, exposing the same loss on interruption.

Returning to the menu and opening another hero in the same process also leaves a stale workshop container because the reset is unwired. Its eventual return uses the then-current `MyPlayer`, not a recorded owner. The exact first UI action that exposes this can depend on which panels the new game closes; the stale state and ownerless return path are the defect, not a claimed observed transfer in gameplay.

### Suggested fix

Give temporary workshop custody an explicit lifecycle. Before exit saving, recover **all** bench/grid items to durable storage, with a conservation-safe fallback if storage is full. Block ordinary autosaves while unpersisted custody exists, or persist that custody in the hero format. Reset workshop state at new-game/teardown boundaries **after** resolving ownership. Merely calling the current reset before saving would intentionally clear and lose the items.

### Regression that fails today

In an isolated test save directory, deposit distinct seeded items into the bench and craft grid; save through the real exit path; destroy the game; start a new process and load the same hero. Assert the exact item multiset survives. Repeat with full inventory and stash. Separately switch A → B within one process and assert B never receives A's items and no workshop state remains open. A smaller wiring check already fails structurally: the reset has no production call site, and neither save predicate nor exit path handles workshop custody.

The external `DISABLED_WorkshopBenchDoesNotReachAnotherHeroSlot` probe encountered SEH while returning an item in a partial headless fixture. This is **not** reported as a product crash or successful save-loss reproduction; it needs a fully initialized game fixture.
