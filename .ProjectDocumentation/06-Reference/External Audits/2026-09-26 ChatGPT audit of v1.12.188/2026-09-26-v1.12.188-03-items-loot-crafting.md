# Audit 3: item conservation, rebuilding, loot and crafting

Baseline: v1.12.188, commit `acc970335a9c0ecd5287f236fb601f2c8d7a8601`, 2026-09-26.

## ITEM-01 [P1]: stash sort still discards items when repacking fails

Confidence: **confirmed**. Evidence: executed independent packing model **and actual `SortStash` through the production DLL**. No real stash/save was changed.

This is the brief's required STASH-01 recheck. The behavior reported for v1.11.102 is still reproducible at the target commit. I have not established an intervening fix and therefore do not assert that it was fixed and later reintroduced.

Locations:

- `Source/qol/stash.cpp:49`, `Source/qol/stash.h:38`: 100 pages of 10×16 cells.
- `Source/qol/stash.cpp:1784`: the claim that rearrangement must succeed is false.
- `Source/qol/stash.cpp:1787`: live contents and grids are cleared before placement is known to succeed.
- `Source/qol/stash.cpp:1810`: item-placement failure is ignored. Other unchecked fallback calls occur at `:1825`, `:1841`, `:1887`, `:1944`.
- `Source/qol/stash.cpp:2027`: resulting stash is marked dirty and autosave can be scheduled.

### Valid input and observed output

Use 15,801 nonstackable 1×1 magic rings and 33 rare 2×3 armors. A valid original layout consumes 15,999 of 16,000 cells. The production fixture constructs that layout explicitly, chooses a real armor base with a verified 2×3 cursor footprint, and assigns distinct seeds.

Sort places the rings before the rare armor tier and starts that tier on the last empty page. Fragmentation leaves room for only 29 armors. Since failed placement does not roll back and the original storage is gone, four armors disappear.

```text
Before: 15,834 items, 33 armors
After:  15,830 items, 29 armors
```

The independent model and production result agree. This is an extreme-capacity counterexample, not a measured frequency for ordinary stashes.

### Suggested fix and failing regression

Build the new layout transactionally in scratch storage. Commit only after verifying exact conservation, including quantities, affix-bearing identity and all overflow/fallback categories. If no arrangement fits, retain the original stash and report that sorting could not complete. A different greedy ordering alone cannot establish a general conservation guarantee.

`StashSortConservesDenseMixedFootprints` fails today with the values above. Extend it to compare complete item multisets, varied footprints/tier boundaries, charms/material pages and stack quantities, then persist/reload the sorted result in an isolated save directory. The external probe uses a nonlocal player argument to avoid scheduling autosave.

## ITEM-02 [P2]: Mystic rebuild collapses unchanged elemental damage ranges

Confidence: **confirmed**. Evidence: traced Mystic caller and executed production rebuild tests for four affix types.

Locations:

- `Source/oracool/workshop.cpp:2392`: accepting a reroll rebuilds the entire affix list, including unchanged entries.
- `Source/items.cpp:3782`: `RebuildOracoolItemWithAffixes`.
- `Source/items.cpp:3838`: both `power.param1` and `power.param2` are assigned `wanted[i].param1`.
- `Source/items.cpp:1225`, `:1233`, `:1331`, `:1339`: fire damage, lightning damage, fire arrows and lightning arrows use the two parameters as distinct damage endpoints.

### Trigger and consequence

An item has a 3–9 elemental affix. Accept a Mystic change to another affix, causing all entries to be rebuilt. The unchanged elemental affix is applied as 3–3, reducing actual damage, even though its recorded affix retains the original second parameter. The same mistake affects accepting a new range-bearing affix. Selecting the explicit keep-original option bypasses the rebuild and is not this trigger.

The external fixture created a real base item, applied each of `IPL_FIREDAM`, `IPL_LIGHTDAM`, `IPL_FIRE_ARROWS`, `IPL_LIGHT_ARROWS` with parameters `{3,9}`, and rebuilt it with the unchanged record. All four lost their maximum endpoint from 9 to 3. These are hand-authored valid parameter fixtures; no claim is made that an actual random drop with that exact range was rolled during gameplay.

### Suggested fix and failing regression

Replay stored affixes according to their parameter semantics. Some scalar powers use min/max as a random roll interval and require pinning; endpoint or discrete-parameter powers must preserve the second value. Simply replacing every assignment with `param2` risks rerolling scalar powers. Centralize this distinction and test it.

`MysticRebuildPreservesUnchangedElementalAffix` fails for all four powers today. Add real generated multi-affix items, reroll an unrelated affix, and assert every unchanged mechanic remains identical before/after and after save/load. Assert recorded tooltip values match applied numeric fields.
