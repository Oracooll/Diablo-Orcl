# Audit 4: rifts, travel, levels and monster identity

Baseline: v1.12.188, commit `acc970335a9c0ecd5287f236fb601f2c8d7a8601`, 2026-09-26.

## WORLD-01 [P2]: closing a rift leaves an ordinary town portal pointing into it

Confidence: **confirmed** for stale portal state and the unguarded return route. Evidence: executed production close/portal-state probe plus code tracing. The resulting level was not visited interactively; no crash or softlock is claimed as reproduced.

Locations:

- `Source/oracool/stonegate.cpp:225`: `CloseStonegate` removes special rift missiles and calls `EndRift`, but does not deactivate ordinary portals targeting the rift.
- `Source/oracool/stonegate.cpp:61`: special portal-missile removal does not cover the normal town portal record.
- `Source/oracool/rift.cpp:229`: `EndRift` resets the rift's seed/kind and associated state.
- `Source/oracool/rift.cpp:663`: the completed Nephalem closing countdown invokes this close path, including while the hero is in town.
- `Source/portal.cpp:135`: `GetPortalLevel` accepts the portal's saved set-level destination without validating whether that rift still exists.
- `Source/levels/setmaps.cpp:177`: entering a rift set-level calls `BuildRiftLevel`.
- `Source/oracool/rift.cpp:364`, `:551`: generation uses current rift state; population/exit setup returns immediately when `InRift` is false.

### Trigger and consequence

Open a town portal inside a rift, return to town and leave it active. Let a cleared Nephalem rift's countdown expire. The rift state is gone, but its ordinary portal remains a valid engine portal. Entering it can route into a rift set-level with reset generation state rather than the former active rift. The saved portal coordinates/world state and current seed no longer have a valid common rift instance. The normal active-rift setup cannot repair this because `InRift` is false.

The production test opens a Nephalem rift, activates a normal portal targeting its set-level, and calls `CloseStonegate`. It verifies `ActiveRift() == None`, then fails because `PosOkPortal` still returns true for the old destination. This isolates the same close function called by the countdown. It does not run dungeon generation or a full portal transition.

### Suggested fix and failing regression

Invalidate ordinary portal records and their visible missiles when their target rift closes or is replaced. Validate rift instance/destination again at portal entry, including already queued travel. Preserve unrelated normal-floor portals. Do not only remove the monument's visual effect.

`ClosingRiftInvalidatesItsTownPortal` fails today. Extend it through the actual sixty-second closure, returning from town, Guardian closure, and replacing a rift of the same kind. Assert no stale entry is possible and unrelated portals still work.

## WORLD-02 [P2]: guardian identity can match a monster on another level

Confidence: **likely** for the gameplay reward corruption; **confirmed by inspection** that the predicate is not level-scoped. Evidence: code tracing only; no guardian-spawn/foreign-floor gameplay reproduction was run.

Locations:

- `Source/oracool/rift.cpp:595`: `IsRiftGuardian` compares active kind, spawned flag and monster slot ID only; it does not require `InRift()`.
- `Source/oracool/rift.cpp:700`: guardian identity is stored as `guardian->getId()`.
- `Source/monster.cpp:4365`: guardian uses the shared active/free monster-slot pool.
- `Source/monster.cpp:1278`: this predicate chooses guardian bonus drop rolls.
- `Source/oracool/treasure_class.cpp:99`: guardian predicate changes treasure quality bonus.
- `Source/items.cpp:5536`: predicate suppresses a monster's scripted unique treasure.

### Trigger and consequence

Spawn a rift guardian, leave the unfinished rift using a town portal or its exit, then visit a normal floor while that rift stays open. Monsters on that floor reuse the same indexed `Monsters[]` storage. If one occupies the saved guardian ID, `IsRiftGuardian` identifies that unrelated monster as the guardian. Its loot path gets guardian treatment; a scripted unique occupying that slot can lose its special treasure.

Leaving an unfinished rift without ending it is deliberate. Retaining a raw slot ID across that transition is insufficient identity. The separate `OnRiftMonsterKilled` routine does check `InRift`, so this report does **not** claim that the unrelated kill completes the rift or awards its keystone.

### Suggested fix and regression

At minimum require the correct active rift level in the shared predicate. Prefer an instance/generation identity if same-set-level replacement or slot reuse can outlive the guardian. Audit every reward consumer of the predicate.

In a fully initialized fixture, spawn the guardian, save its slot, leave the rift while retaining its state, and initialize a non-rift monster in that slot. Assert `IsRiftGuardian` is false and its normal treasure behavior is retained. The predicate fails that assertion today once those preconditions are established. Also assert the genuine guardian remains recognized when returning to its still-active rift. This proposed test was not executed in this audit.
