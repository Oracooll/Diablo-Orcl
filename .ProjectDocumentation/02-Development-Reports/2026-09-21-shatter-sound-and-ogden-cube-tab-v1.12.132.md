# The item-break sound was in the archive all along — v1.12.132

**Date:** 2026-09-21
**Version:** v1.12.132
**Branch:** renderer-32bit

## The correction

I told the user there was no item-break sound in the engine. They pushed back:

> there is definitely Item Broken sound in the game. Sounds like glass braking. It is in vanilla
> game i am sure. I am not sure if it is in devilutionx. Check again.

They were right. **`sfx\misc\shatter.wav` is in diabdat.mpq** — 44262 bytes — and DevilutionX has no
`_sfx_id` for it, so it has never been played by this engine or upstream.

**Why the first answer was wrong.** I searched `effects.h` and `effects.cpp`, which list the sounds
the code *uses*, and concluded the sound did not exist. What the code references and what the
archive holds are different sets, and the gap between them is exactly where an unused asset lives.
The right tool was sitting in `tools/`: `oracool_mpq_extract.exe` takes a manifest of names and
reports which ones the archive has. A fifteen-name guess list found it on the first run.

The lesson generalises past sounds: **for anything shipped in the original game, ask the archive, not
the source.** The source is a lower bound on what exists.

## Wiring it

```cpp
// effects.h, appended at the END before SFX_NONE
IS_SHATTER,
// effects.cpp
/*IS_SHATTER*/    { sfx_MISC,                  "sfx\\misc\\shatter.wav",      nullptr },
```

Appended rather than inserted beside the other `sfx\misc` entries, because `sfxdata[]` is indexed by
this enum's order: a value inserted in the middle silently repoints every sound after it, and the
failure would be every late sound playing the wrong file rather than a compile error.

## The 0-durability break

> There should be one played when an item reaches 0 durability and gets destroyed.

There was none — `BreakOrRemoveEquipment` sets the durability to zero, marks the item broken and
schedules a save, in silence. `PlaySFX(IS_SHATTER)` now goes with it, on the single-player path where
the item stays worn and broken.

## Ogden's Cube tab

> for ogden missing recipes we will need Cube tab canvas [...] Use the transmute button as with
> Levski's Cube. Same behaviour.

Measured, and it is Levski's page to the pixel: frame **x 118..224, y 406..541**, rules at x
156/185/214 and y 444/473/502, so the grid is **3×4 at (128,416)**. "Same behaviour" therefore cost
one asset and one line of a table:

```cpp
constexpr ListSkinGeometry OgdenCubePageGeometry {
	{ 340, 720 }, { 128, 416 }, CubePageTransmuteRect, ... OgdenCubeCanvasAsset, ...
};
```

He gets the same Griswold Refresh plate as Transmute at the same derived position — the grid frame's
centre, four pixels below its foot.

The tab table generalised with him: `TabbedPageAt(index)` now answers for **two** hosts. Levski has
both pages painted, so his second tab is the recipe panel; Ogden's second tab keeps the page he had
until his own recipe canvas arrives (it did, mid-build — v1.12.133).

This is where his four item-in-hand recipes are worked: Free the Sockets, Temper Jewels, Punch
Sockets and Recolour Gems. None of them acts on a collection, which is why they cannot live on his
Gems or Runes pages.

## The arrows, for the next build

Griswold's sell glyph is an arrow pointing LEFT. In screen coordinates a clockwise quarter turn
sends left to UP and an anticlockwise one sends it DOWN, so `Rotate90FlipNone` is the upgrade and
`Rotate270FlipNone` the downgrade. Rotating the DELIVERED glyph rather than drawing new ones keeps
the shadow, the weight and the palette identical to his — which is the whole point of reusing his
button.
