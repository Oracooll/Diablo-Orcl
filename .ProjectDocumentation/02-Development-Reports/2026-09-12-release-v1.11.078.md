# Cutting v1.11.078, and the compiler that moved house

2026-09-12

## What was asked

Two things, in order. First "upload all on github - builds and the wiki". Then, after I reported
that the newest release asset was six days and seventy-eight builds stale: "yes, cut the v1.11.078
release zip."

## The push

`renderer-32bit` was 49 commits ahead of origin and the tree was clean, so one push carried
everything - my source work from v1.11.060 to v1.11.078 *and* the other session's wiki commits,
since both land on the same branch. `oracool-v1-main` was already in sync and stayed frozen.

Worth writing down because it was the first question the user asked afterwards: **a push ships no
game.** `.exe`, `.dll` and `.mpq` are untracked by design, so GitHub had the sources that produce
the binary and not the binary. A playable download is a Release with an attached asset, which is a
separate act.

## The compiler moved house

`cmake --build` would not run. The failure was three layers deep and each layer lied differently:

- the Bash tool's `cmd /c "..."` opened an interactive shell instead of running the chain, twice,
  silently - it printed the Windows banner and a prompt and exited 0
- routed through a `.cmd` file and PowerShell's call operator instead, the real error surfaced:
  `The system cannot find the path specified` followed by `'cmake' is not recognized`
- the cause: **`C:\Program Files\Microsoft Visual Studio\2022\Community` no longer exists.** The
  install is now `...\Microsoft Visual Studio\18\Community`, carrying CMake 4.3

So the vcvars incantation in my memory note was stale, and the way it failed - vcvars not found,
therefore no cmake on PATH, therefore "cmake is not recognized" - points at the second error rather
than the first. `-vcvars_ver=14.52` still resolves under VS 18, so the MSVC pin survives the move.

The lesson for the next time: when `cmake` is "not recognized", the suspect is the vcvars line
above it, not the build.

## The version was a build behind

`ORACOOL_VERSION` said 1.11.078 but `build\x64-Release\DiabloOrcl.exe` carried a VERSIONINFO stamp
of **1.11.077** - the concurrent session's build, made after mine. `BuildReleasePackage.ps1` catches
exactly this and refuses to package a stale binary, which is what it was written for. CMakeLists
lists `ORACOOL_VERSION` in `CMAKE_CONFIGURE_DEPENDS`, so a plain build reconfigured and restamped;
no manual configure was needed. The rebuild also repacked `oracool.mpq` (466 files, 48.2 MB).

## Verified, then packaged

The Release tree has no tests configured (`ctest -N` reports 0 - tests are a Debug-config target),
and the toolchain had just changed under the code, so the binary was no longer built by the compiler
the suite last ran against. That is a reason to re-run it rather than to trust the earlier green:
Debug rebuilt and **720/720 passed**, one timedemo skipped as always.

`tools\BuildReleasePackage.ps1` then passed every gate it owns - both archives verified by content
rather than timestamp, the exe's resource equal to `ORACOOL_VERSION`, seven Blizzard archives absent,
no loose folders, and the finished zip's entry list compared by name against staging. 11 files,
**51.6 MB**.

The zip is 12 MB larger than v1.10.001's 39 MB, and that is the private archive's dissolution
showing up on the scales: art that used to ride in `oracool_private.mpq` outside the repository now
ships in `oracool.mpq` inside the package.

## The release

`v1.11.078`, tagged on `renderer-32bit`, notes written from the 121 commits since v1.10.001 and
grouped by what a player would notice - the four renderer stages, the Paladin, items, the interface,
the area ladder, the dissolved archive, the wiki. It is the latest release, not a prerelease.

https://github.com/Oracooll/Diablo-Orcl/releases/tag/v1.11.078

RTM was then refreshed from the Release tree: the exe was the 1.11.077 one, both archives already
matched by hash. No game process was running, so nothing had to be waited on.
