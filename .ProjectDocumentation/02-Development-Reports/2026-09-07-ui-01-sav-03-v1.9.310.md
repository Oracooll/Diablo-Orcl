# UI-01 and SAV-03 from the external audit (v1.9.310)

**Date:** 2026-09-07. The user: "do UI-01 and SAV-03 too."

## UI-01: the F-key bound the previous frame's hover

The skill picker recorded the hovered cell during its DRAW, and the F-key handler read that: move the cursor from A to B and press before the next frame, and A was bound; move off every cell and press, and the last cell was. The click handler carried its own copy of the cell walk. Both now share one: `ForEachPickerCell` walks the visible cells in draw order, `PickerEntryAt` answers "which entry is under this point", the click uses it, and the new `RefreshSkillPickerHover` resolves the hover from the CURRENT mouse position at key time - the handler calls it first. `GetSkillPickerCellCenter` exposes cell centres for tests. Test: a Sorcerer who knows Firebolt; the hover names Firebolt at its cell, names something else at cell 0 without any draw, and nothing off the cells.

## SAV-03: the full-save loader trusted the class and the backpack count

`LoadPlayer` read `_pClass` and, when the block bonus was zero, indexed `PlayersData` with it unchecked; `_pNumInv` was read and used as a loop bound unclamped. Both fail the load with a message now (a controlled `app_fatal`, the loader's existing idiom for a save it cannot honour), before anything indexes by them. Not clamped: a wrong class is not a character to repair. No unit test: the loader reads through a save archive and the existing tests note that building one just for a test is not worth the machinery (loadsave_test.cpp).

Suite 647/648, the standing dungeon-generation failure only.
