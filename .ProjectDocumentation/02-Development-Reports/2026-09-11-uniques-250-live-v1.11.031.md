# All 250 expansion uniques live, on 18 new bases (v1.11.031)

**Date:** 2026-09-11
**Branch:** renderer-32bit, local commits only

The user asked "what is stopping you from doing it now while waiting for new batches from GPT?" about the 107 uniques waiting on item bases. Nothing was stopping me. Two rulings came in while I worked: "NO NEW ITEM SLOTS. convert to one of existing ones", then "I am ok with new item bases".

## What changed

The package's 107 remaining uniques sat on 18 `BASE_*` tokens the engine had no `unique_base_item` for. Each token now has its **own** unique type, carried by **one new base in an existing slot**:

| Slot | New bases |
|---|---|
| Gloves | Gloves, Gauntlets |
| Boots | Boots, Greaves |
| Belt | Sash, War Belt |
| Shoulders | Pauldrons, Shoulder Mantle |
| Body armour | Travelling Cloak, Battle Cloak |
| Amulet | Relic, Reliquary |
| One hand | Spear (sword family, 1x3) and War Lute (mace family, 2x3) |
| Two hands | Pike (axe family, 2x3) |
| Shield hand | War Quiver, Canticle, Arcane Focus (2x2) |

Stats are the package's own for each base. A requirement is kept only where the package names a single stat. Each base wears its first unique's sprite until its own icon arrives (RfA-04), which keeps the inventory footprint right.

The generator (`tools/GenUniqueItems.ps1`) maps each `BASE_*` token to its type. It emits the 107 as a **late group after the 143**, so no existing `_iUid` moves. Their icons are a second run, `unique_items2_curs*.inc`, numbered in the enum after the charm icons. The 107 frames were built with ItemIconCel in `asis` mode and **appended** to `oracool_items.cel` (501 to 608), leaving every existing frame byte-identical. The generator re-extracts its sprite zip on each run, so its Temp inputs are fine.

## The save-safety lesson (the first attempt broke 26 tests)

The first attempt mapped tokens onto EXISTING types: gloves onto the Leather Gloves, relics onto the amulet, cloaks onto vanilla's Cloak and Cape. It also made six new bases droppable everywhere. 26 pack and hero tests failed. A golden "Platinum Sword of vampires" came back as "Jade Great Helm of the wolf". The reason is that items are **not stored, they are rebuilt from their seed**:

- **Vendor stock** re-picks its base from the shop's pool (`RecreateTownItem`). A new base in that pool changes what an already-bought item rebuilds into.
- **A unique** is re-chosen among all uniques of its base's type (`CheckUnique` with `recreate`, which takes the highest-numbered match). New uniques on an existing type would become that choice for items that already exist, and a magic item whose unique roll found nothing could now find one.

Characters carry items across games (see `project_v1_always_new_game_no_continue`), so this would have changed real gear. The redo:
- It adds nothing to any existing type's unique list.
- It restores the four Leather rows byte-for-byte.
- It keeps the new bases out of every shop pool (`IsUniqueExpansionBase` in `RndVendorItem`), so they drop only in the dungeon.

**All 699 tests pass with no expected value changed**, which is the proof that saved items rebuild as before.
