# 1.8.24 - The book that fell off the screen

A screenshot review of Levski's Roar at 1.8.23. Two defects, both visible only in the running game.

## 1. The recipe book was drawn off the left edge

The book's title rendered as *"IPES"* and every line lost its first characters. The rect was:

```cpp
window.position.x - RecipeBookWidth - SlotGap
```

with a comment asserting *"there is always room on the left - the window is centred"*. That
reasoning is wrong, and wrong in a way worth recording: **centring guarantees symmetry, not space.**
The room to the left of a centred window is `(gnScreenWidth - WindowWidth) / 2`, which at 1024 wide
is 408px against a book needing `420 + 6`. The window being centred says nothing about whether
anything else fits beside it.

Now: prefer left, fall back to the right of the window if left does not fit, then clamp into the
screen regardless. A book too wide for either side is still fully readable, merely overlapping - the
one outcome that is never acceptable is text drawn at a negative x, because nothing on screen tells
the player it is there.

## 2. The panel was still see-through, and unevenly

1.8.21 stacked two half-transparent passes on the panel ground after the first screenshot review.
The second screenshot shows why that was the wrong shape of fix: the four cells sitting over a lit
doorway glowed orange while the rest sat near-black, so the grid read as four different materials.
Half-transparency composites against what is behind it, and what is behind this window is a moving,
unevenly lit town. More passes would only have made it darker, never even.

`DrawPanelGround` is now a solid `FillRect`. Every other window in the game sits on painted art and
hides what is under it completely; this one has no art yet, and "no art" should still mean "not a
window you can see through".

The colour comes from the 16-shade grey ramp in the **shared upper half of the palette (128-255)**,
which is identical across town and all four tilesets - the same discipline `DrawOrnateBorder`
follows, so the fill cannot recolour itself by level.

## 3. The cells now read as wells, not as decoration

Carried in the same pass, since it was one parameter once the fill was solid. The panel is
`PAL16_GRAY + 12`, the cells `PAL16_GRAY + 15`. Previously both were the same colour with only a
border between them, which is exactly why the cells read as squares drawn on stone rather than as
places to put a stone. This closes the "grid cells read as decoration" note that had been parked as
an art-pass job - it turned out to need two palette indices, not art.

## What the shot confirmed working

Both close buttons from 1.8.22 landed where intended and are clearly hittable, and the recipe book
carrying its own X - closing the book rather than the window under it - behaved correctly on its
first real test.

## Note on method

Three of the last four defects in this window were invisible to every check that can be run without
the game: the geometry compiled, the constants were right, the tests passed. **A window drawn over
the world can only be verified by a screenshot.** That is now true three times running here, and it
is worth treating as a rule rather than as three coincidences.

## Verification

Debug build clean. **454 tests, the usual two** (`Drlg_l1.CreateL5Dungeon_diablo_3_844660068`,
`Timedemo.WarriorLevel1to2`). Run the suite serially; under `-j` the loadsave tests collide over a
shared save path.
