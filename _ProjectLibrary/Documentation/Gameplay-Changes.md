### Acceptance correction

- The initial port allowed purchases to disappear correctly but inherited Griswold's quest-base exclusion when listing the purchased unique for resale. Unique Shop merchandise is now explicitly marked as smith merchandise and is eligible for resale even when its underlying base item ID belongs to the protected quest range. Actual quest items remain excluded.
- On 2026-08-04, the user reported that most Unique Shop purchases also vanished with "sent an invalid packet" when dropped on the ground - the same symptom class as the debug-drop bug fixed in v0.1.11, but from a completely different source. Root cause: the resale-marker fix above (`CreateUniqueVendorItem`, `items.cpp`) stamps each purchase's `_iCreateInfo` with both `CF_UNIQUE` and `CF_SMITH` set together, so `stores.cpp` can later recognize it as Smith-sourced for resale - but vanilla's `IsCreationFlagComboValid` (`items/validation.cpp`, shared by the same drop-safety check `IsPItemValid` uses) rejects *any* town-flagged item that carries more than one flag, and never anticipated `CF_UNIQUE` being one of them. That single check runs first and unconditionally for every dropped item, so it silently rejected 100% of Unique Shop purchases the instant they were dropped - never partial or tier-specific, unlike the debug-drop bug. Fixed by excluding `CF_UNIQUE` before applying vanilla's "only one towner flag" rule, so the resale marker and the drop-safety check no longer conflict; a real item improperly claiming two different vendors at once is still rejected exactly as before. Separately confirmed the real `UniqueItems` table's `UIMinLvl` never exceeds 27, well under the unrelated town-item level ceiling (30) the next check in the same chain applies, so no Unique Shop item was ever at risk of failing on level grounds once this flag conflict is resolved.
- Correction verification: new `IsCreationFlagComboValid` tests confirm the `CF_UNIQUE`+`CF_SMITH` combo now passes, that two genuinely different town flags (with or without `CF_UNIQUE`) still correctly fail, and that every level in the real `UniqueItems` table's 1-27 `UIMinLvl` range survives both checks `IsPItemValid` runs in sequence for a town item. All 163 tests across the six directly-touched regression suites pass. Version bumped to 0.1.12.

## OE-006: Gold Stacks Buff

- Status: User verified
- Scope: Single-player inventory gold stacks
- Change: Raises the maximum value of one inventory gold stack from 5,000 to 65,535.
- Limit rationale: 65,535 is the maximum unsigned 16-bit value stored in the existing `ItemPack.wValue` field. A higher stack would be truncated during character saving, so it is not safe without a save-format change.
- Integration: Existing pickup, merging, automatic placement, splitting, shop-payment, stash-withdrawal, cursor, and total-gold paths already use the shared runtime stack limit and therefore inherit the new cap.
- Auric Amulet: The buff supersedes the amulet's normal 10,000 stack benefit while enabled because 65,535 is already the format maximum.
- Compatibility: Disabled and multiplayer games retain the vanilla 5,000 limit, including the Auric Amulet's existing 10,000 behavior. No save-format change is introduced.
- Configuration: `Gold Stacks Buff=1` in `[Oracool Edition]`; enabled by default and applied when starting or loading a game.
- Verification: The complete Debug build succeeds, the 65,535 packed-item round trip has focused automated coverage, and all 214 automated tests pass.

### Acceptance correction

- Initial user testing exposed a second, hard-coded 5,000 clamp in recurring player validation. A large stash withdrawal was first placed into one enlarged stack, then immediately truncated to 5,000 while the stash had already deducted the full request.
- Player validation now uses the active shared stack limit. Stash withdrawal also deducts only the amount actually placed and immediately recalculates the carried-gold total, so insufficient inventory capacity cannot destroy gold.
- Correction verification: focused partial-withdrawal coverage passes and the complete suite passes all 215 tests.
- User acceptance: On 2026-08-02, the corrected build passed the user's full practical testing with no further problems found.

## OE-008: Rare Items

- Status: User verified
- Scope: Single-player procedurally generated item tier, built on the OE-016 extended item-data foundation
- Base items: Rare items are derived from normal white base items, drawing affixes from vanilla's own `ItemPrefixes[]`/`ItemSuffixes[]` tables — mechanically the same primitives (`SaveItemPower`, `PLVal`) an ordinary magic item uses, just with more than the vanilla one-prefix/one-suffix limit.
- Name color: `UiFlags::ColorYellow`, visually distinct from white normal items, blue magical items, and gold Unique items.
- Naming: `Rare {base item name}`, falling back to the item's short name if the full name doesn't fit the panel (same `StringInPanel` check vanilla magic-item naming already uses).
- Affixes: Always at least one prefix and one suffix; up to two of each (four total). A second prefix and a second suffix each independently have a 30% chance to also roll, so the distribution is weighted toward fewer total affixes (roughly 49% two-affix / 42% three-affix / 9% four-affix) — confirmed by the user as the desired shape. No affix type can repeat on one item, and vanilla's Good/Evil (`PLGOE`) conflict rule applies across every affix on the item, not just one prefix/suffix pair.
- Identification: Rare items do not force any identification state of their own. Like every other item, whether they drop already identified is governed entirely by the existing `Auto Identify Drops` toggle (OE-003) — with it enabled, all drops (including Rare items) are identified; with it disabled, Rare items need a scroll or Cain like anything else. This was an explicit correction from the user: no per-tier identification special-casing, every item follows the one shared setting.
- Pricing: A new `CalcRareItemValue` sums every stored affix's contribution against the item's base value — vanilla's `CalcItemValue` only has two value-accumulator slots (`_iVAdd1/_iVMult1`, `_iVAdd2/_iVMult2`), which cannot represent up to four independent Rare affixes, so Rare items don't use those fields at all; their rolled affix values live in `Item::_iOracoolPrefixes`/`_iOracoolSuffixes` instead (the OE-016 foundation).
- Drop frequency: Controlled by a new adjustable option (below), checked only after an item has already failed its Unique roll and before falling through to ordinary Magic generation — Rare generation never reduces or replaces Unique frequency.
- Statistics display: Hovering a Rare item reuses the engine's existing floating Unique-item statistics popup (`ShowUniqueItemInfoBox`/`DrawUniqueInfo`), generalized to branch on tier: a Rare item's popup lists its own stored affixes (via the same `PrintItemPower` line formatter Uniques already use) instead of a static `UniqueItems[]` table entry.
- Interface priority: The floating popup now renders after every other open panel/dialog (spell list, gold-split/withdraw, help, chat log, message toast) instead of before some of them, so it is genuinely always-on-top — this fix applies to vanilla Unique item hovers too, not just Rare items, per the roadmap's explicit requirement.
- Store integration: Store listings (`PrintStoreItem`) show a Rare item's full affix list on its bonus line, the same comma-joined style already used for magic items' single prefix/suffix; store selling, repair, and recharge all work unchanged since none of those gate on item quality in a way that would exclude a magic-quality Rare item.
- Configuration: `Rare Item Drop Chance=8` (percent) in `[Oracool Edition]`, alphabetized directly after `Belt Mod`; adjustable 0-100 without a code change. Zero disables Rare generation entirely; existing Rare items on a save remain intact and usable regardless of the current setting.
- Compatibility: Single-player only (`oracool::IsSinglePlayer()`), multiplayer is completely unaffected regardless of the option. No additional save-format change beyond the OE-016 foundation already in place.
- Two implementation defaults chosen without a dedicated user decision (narrower engineering calls, not balance/product calls — flagged here for easy revisiting): eligible item classes/slots are exactly whatever vanilla magic items already support (no new restriction), and the 30% per-slot bonus-affix probability is not yet exposed as its own setting.
- Verification: The complete Debug build succeeds. New coverage in `test/items_test.cpp`: a Rare item always ends up with at least one prefix and one suffix (200 trials), never duplicates an affix type on one item (200 trials), the 2/3/4-affix distribution is weighted toward fewer over 1,000 trials, `CalcOracoolTieredItemValue` (renamed from `CalcRareItemValue` when Buffed Uniques started sharing it — see OE-009) sums affix contributions correctly and never produces a non-positive price, and `getTextColor()` returns yellow for a tiered item regardless of its underlying magic quality.
- Deferred: In-game manual acceptance has not yet been performed (see checklist in Testing-Guide.md). No automated test for the popup's visual rendering or z-order — flagged for manual QA, consistent with prior features' pixel-rendering exclusions.

### Acceptance correction

- On 2026-08-04, the user tested Rare, Buffed Unique, and Primal generation together using developer test characters and the debug console's `drop rare`/`drop unique`/`drop primal` commands. Rare items specifically worked exactly as intended with no issues found; the three bugs reported that session were all in Buffed Unique/Primal-specific behavior (see the OE-009 and OE-010 corrections below).
- Later the same day, the user found a further bug affecting Rare too: a jewelry item (rings/amulets, a much smaller affix pool than weapons/armor) could drop with fewer than the guaranteed 1 prefix + 1 suffix when its level window happened to be narrow. Same root cause and fix as the OE-009 correction below (`GetTieredItemAffixes`'s minimum-affix loop now always ignores the level window). Verified with a new `GetRareItemAffixes_AlwaysProducesAtLeastOnePrefixAndSuffixForJewelryInNarrowLevelWindow` test.

## OE-009: Buffed Uniques

- Status: User verified
- Scope: Single-player procedurally generated item tier, sharing almost all of its plumbing with Rare Items (OE-008) — the affix engine, popup, store display, pricing, and color infrastructure needed no changes beyond generalizing away from "Rare-only" naming.
- Vanilla separation: Existing predefined vanilla Unique items (`UniqueItems[]`, `GetUniqueItem`) are completely untouched — Buffed Uniques are a separate, procedurally generated population, not a modification of the static catalogue.
- Item foundation: Derived from normal white base items, same as Rare, using the same vanilla `ItemPrefixes[]`/`ItemSuffixes[]` tables and `SaveItemPower`/`PLVal` roll primitives.
- Affix range: At least two prefixes and two suffixes (4 total minimum); at most three of each (6 total maximum) — `Item::MaxOracoolAffixesPerSlot` already caps at 3, matching this exactly. Distribution is weighted toward fewer, same shape as Rare (each of a 3rd prefix/3rd suffix independently has a 30% chance), confirmed by the user: roughly 49% four-affix / 42% five-affix / 9% six-affix.
- Affix rules: Reuses Rare's exact rules by user's explicit choice — no duplicate affix type on one item, and vanilla's Good/Evil (`PLGOE`) conflict exclusion applies across every affix on the item.
- Naming: `Unique {base item name}` (not "Buffed Unique") — deliberately blends with vanilla Unique naming at the display layer, distinguished underneath only by carrying `OracoolItemTier::BuffedUnique` and its own affix list.
- Name color: `UiFlags::ColorWhitegold`, the same gold used by vanilla Unique items.
- Identification: Does not force any identification state of its own — like Rare items (see the OE-008 correction above), it follows the single shared `Auto Identify Drops` toggle uniformly.
- Drop chance: A new adjustable `Buffed Unique Item Drop Chance` option (percent, default 3), independent of `Unique Item Drop Multiplier` — the user's explicit choice over literally tying it to vanilla Unique's own internal roll, for simplicity and direct tunability. Checked in the quality-roll fork *before* Rare (immediately after an item fails its Unique roll): Buffed Unique is meant to be the rarer of the two procedural tiers, so the rarer roll gets first opportunity at the item, and neither roll ever reduces or replaces the vanilla Unique roll's own frequency.
- Implementation: `GetTieredItemAffixes` is a new shared engine (in `items.cpp`) parameterized by tier, minimum affixes per slot, and bonus-affix chance; `GetRareItemAffixes` (minAffixesPerSlot=1) and `GetBuffedUniqueItemAffixes` (minAffixesPerSlot=2) are thin wrappers over it, both feeding the same `CalcOracoolTieredItemValue` (renamed from `CalcRareItemValue`) for pricing.
- Statistics display, store listing, color, and popup z-order: All already tier-agnostic from the OE-008 work (`hasOracoolTier()`-based branching in `DrawUniqueInfo`/`PrintItemDetails`/`PrintStoreItem`/`getTextColor()`), so Buffed Uniques picked all of this up automatically with no additional changes.
- Compatibility: Single-player only (`oracool::IsSinglePlayer()`), multiplayer completely unaffected. No additional save-format change beyond the OE-016 foundation.
- One implementation default chosen without a dedicated user decision (narrower engineering call, flagged for easy revisiting): eligible item classes/slots are exactly whatever vanilla magic items already support, same as Rare.
- Verification: The complete Debug build succeeds. New coverage in `test/items_test.cpp`: always at least 2 prefixes + 2 suffixes (200 trials), never exceeds 3 of either, never duplicates an affix type (200 trials), the 4/5/6-affix distribution is weighted toward fewer over 1,000 trials, and the item is correctly tagged `OracoolItemTier::BuffedUnique`, colored gold, and named `Unique {base}` (not "Buffed Unique {base}").
- Deferred: In-game manual acceptance has not yet been performed (see checklist in Testing-Guide.md).

### Acceptance correction

- On 2026-08-04, the user's testing found the description panel shown under the belt row (`PrintItemDetails`) labeled a Buffed Unique as "rare item" instead of "unique item" — a hardcoded `hasOracoolTier() ? "rare item" : "unique item"` ternary ignored which specific tier the item actually was, defaulting every tiered item to the Rare wording.
- Fixed with a new `GetOracoolTierPanelLabel(OracoolItemTier)` helper (in `items.cpp`, declared in `items.h` for direct test coverage) returning the correct wording per tier: "rare item" for Rare, "unique item" for Buffed Unique (matching vanilla Unique's own wording, since Buffed Unique is meant to visually blend in), and "primal item" for Primal. `PrintItemDetails` now calls this helper instead of the broken ternary.
- Correction verification: a new `GetOracoolTierPanelLabel.ReturnsDistinctWordingPerTier` test asserts all three wordings directly, and the complete suite passes all 279 tests.
- On 2026-08-04, the user found a second bug: a Buffed Unique ring dropped with only 1 affix total, well under the guaranteed minimum of 2 prefixes + 2 suffixes (4 total). The user asked for the affix-count limits on all three tiers to be re-checked against the roadmap. Root cause: `GetTieredItemAffixes`'s forced-minimum loop silently accepted fewer than the requested count whenever candidate selection ran dry, exactly the same mechanism as the Primal affix-count bug fixed earlier that day (see OE-010) - but that fix only forced `ignoreLevelLimits` for `perfectRoll` items (Primal), leaving Rare and Buffed Unique still exposed to the same starvation whenever a narrow-pool item class (jewelry: rings/amulets, using `AffixItemType::Misc`, a far smaller affix table than weapons/armor) combined with a narrow level window.
- Fixed by always ignoring the level window inside the forced-minimum loop, for every tier, regardless of `perfectRoll` or the `ignoreLevelLimits` argument - the minimum affix count is a stated design guarantee ("Always at least...") in every tier's roadmap wording, not a best-effort. The optional bonus-affix rolls above the minimum still respect the level window as before, since those are explicitly probabilistic extras, not a promise. The duplicate-affix-type and Good/Evil exclusion rules are untouched for both the mandatory and bonus rolls.
- Correction verification: new `GetBuffedUniqueItemAffixes_AlwaysProducesAtLeastTwoPrefixesAndTwoSuffixesForJewelryInNarrowLevelWindow` and `GetRareItemAffixes_AlwaysProducesAtLeastOnePrefixAndSuffixForJewelryInNarrowLevelWindow` tests (200 trials each, `AffixItemType::Misc`, minlvl=maxlvl=1 - the narrowest possible window on the smallest affix pool) confirm the guarantee holds, and the complete suite passes all 281 tests.

## OE-010: Primal Items

- Status: User verified
- Scope: Highest single-player procedurally generated item tier, sharing the same affix/popup/pricing/store infrastructure as Rare (OE-008) and Buffed Unique (OE-009).
- Affixes: Always exactly three prefixes and three suffixes (fixed, not a range) — `GetTieredItemAffixes` is called with `minAffixesPerSlot = Item::MaxOracoolAffixesPerSlot` (3), so the shared engine's "bonus affix" roll can never fire since the count is already at the hard cap the moment the forced minimum is applied.
- Perfect-roll rule: Every affix's magnitude is forced to the maximum end of its declared range instead of being randomly rolled, and every affix is guaranteed beneficial (no curse/drawback-type affix can ever be selected on a Primal, regardless of the caller's `onlygood` context) — a maxed-out curse would contradict "perfect roll" being an unambiguous upgrade. The item's durability is also forced to full, overriding the normal random `ItemRndDur` roll that runs for every other magic-quality item. `Item::_iOracoolPerfectRoll` (already present from the OE-016 foundation, previously unused) is set to `true`.
- Implementation of the "always maximum" roll: a new file-scoped `ForcePerfectAffixRoll` flag, checked by the shared `RndPL` roll primitive (returns the range's upper bound directly instead of calling `GenerateRnd` when set). Set only for the duration of `GetTieredItemAffixes`'s affix-application step when `perfectRoll=true`, and always restored to its previous value afterward — verified by a regression test that a Rare generation immediately following a Primal generation still produces below-maximum rolls.
- Naming: `Primal {base item name}`, using the same shared naming path (`GetOracoolTierLabel`) as Rare (`Rare `) and Buffed Unique (`Unique `).
- Name color: `UiFlags::ColorOrange` — not literally cyan as the original roadmap wording specified. True cyan isn't available: `UiFlags` is a fully-packed 32-bit flag enum with zero free bits (widening it to 64-bit would touch a pervasively-used core UI type), and no cyan font recolor asset (`.trn`) exists anywhere in the game's data files, so a new one would need to be created without any way to visually verify it short of the user launching the game. The user chose Orange as the practical alternative, noting it also matches Diablo 3's own convention of orange for Primal Ancient/Legendary items.
- Drop chance: A new adjustable `Primal Item Drop Chance` option (percent, default 1) — the same independent-percentage mechanism as Rare and Buffed Unique, not literally tied to `Unique Item Drop Multiplier` as an early roadmap draft suggested (consistent with the precedent already set for Buffed Unique). Checked *before* Buffed Unique and Rare in the quality-roll fork (immediately after failing the vanilla Unique roll) — Primal is the rarest and most powerful tier, so it gets first opportunity at the item, and none of the three tiered rolls ever reduces or replaces the others' frequency.
- Identification: Follows the single shared `Auto Identify Drops` toggle uniformly, same as every other item and every other tier — no per-tier special-casing.
- Statistics display, store listing, and pricing: All already tier-agnostic from the OE-008/OE-009 work, picked up automatically with no additional changes.
- Compatibility: Single-player only (`oracool::IsSinglePlayer()`), multiplayer completely unaffected. No additional save-format change beyond the OE-016 foundation (which already reserved `OracoolItemTier::Primal` and the `_iOracoolPerfectRoll` field for exactly this).
- One implementation default chosen without a dedicated user decision (narrower engineering call, flagged for easy revisiting): eligible item classes/slots are exactly whatever vanilla magic items already support, same as Rare and Buffed Unique.
- Verification: The complete Debug build succeeds. New coverage in `test/items_test.cpp`: always exactly 3 prefixes + 3 suffixes, never duplicates an affix type, every affix's stored value matches some table entry's `maxVal` for that affix type (cross-checked directly against `ItemPrefixes[]`/`ItemSuffixes[]`, which needed `DVL_API_FOR_TEST` added to be linkable from the test binary), every selected affix is beneficial (`PLOk`), the item is tagged `OracoolItemTier::Primal` with `_iOracoolPerfectRoll=true` and colored orange, and the perfect-roll flag doesn't leak into a subsequent Rare generation.
- Deferred: In-game manual acceptance has not yet been performed (see checklist in Testing-Guide.md).

### Acceptance correction

- On 2026-08-04, the user's testing found two bugs specific to Primal items:
  1. The description panel under the belt row labeled Primal items as "rare item" instead of "primal item" — the same root cause and fix as the OE-009 Buffed Unique correction above (`GetOracoolTierPanelLabel`, now called from `PrintItemDetails`).
  2. Some Primal items dropped with fewer than 6 total affixes, even though the design guarantees exactly 3 prefixes + 3 suffixes always. The affixes actually present were confirmed correctly max-rolled — the bug was isolated to the count guarantee, not the roll magnitude. Root cause: `GetTieredItemAffixes`'s forced-minimum affix loop silently accepts fewer than the requested count whenever candidate selection returns no eligible affix, and a narrow/low level window (as commonly produced by a low-level drop) starves that candidate pool well before the duplicate-type and beneficial-only rules alone would.
- Fixed by forcing `ignoreLevelLimits = true` whenever `perfectRoll = true` inside `GetTieredItemAffixes`, alongside the existing `onlygood = true` forcing — a "perfect roll" item (currently only Primal) is meant to guarantee its full affix count every time, and the level window was the dominant cause of candidate pools running dry. The duplicate-type and Good/Evil exclusion rules are untouched.
- Correction verification: a new `GetPrimalItemAffixes_AlwaysProducesExactlyThreePrefixesAndThreeSuffixesInNarrowLevelWindow` test (200 trials, minlvl=maxlvl=1) confirms the guarantee holds even in the narrowest possible level window, and the complete suite passes all 279 tests.

## OE-011: Torment Difficulty

- Status: Build-verified (186 automated tests: items_test 51, inv_test 49, stores_test 10, loadsave_test 8, player_test 5, pack_test 58, missiles_test 5). Not yet manually tested in-game.
- Scope: New single-player-only difficulty above Hell - the final item in the project's original approved roadmap (see `Project-Scope.md`).

### Research: measuring the actual Normal->Nightmare->Hell progression before extending it

Before designing anything, every difficulty-dependent formula in the codebase was traced to its exact numbers (see the research notes folded into this section below). Key finding: damage and monster experience both scale by a clean **x2 per tier** (1x -> 2x -> 4x), the most consistent pattern in the whole system. Monster HP and armor class don't follow as clean a ratio - the original multipliers (3x/4x for HP, +50/+80 flat for AC) look tuned more by feel than by a single formula. Given that, and the user's own design (one adjustable multiplier applied on top of Hell, not a new per-stat formula), the multiplier's initial default of **2.0** continues the one genuinely consistent pattern actually found in the data.

### Decisions locked in with the user before implementation

- **Unlock gate**: a toggleable character-level requirement, applied to *all four* difficulties in single-player (which previously had no gate of any kind) - Nightmare 15, Hell 30, Torment 40. The existing multiplayer-only gate (level 20/30) is untouched.
- **Torment Difficulty Multiplier default**: 2.0 (see above).
- **Player-side penalty**: none. Torment stays a monster/treasure difficulty multiplier; no difficulty-based resistance cap or stat penalty exists anywhere in this codebase today, and none was added.

### Core mechanism: one multiplier applied on top of Hell's own formulas

Two consistent rules apply everywhere a Hell-tier formula exists, rather than inventing a fifth arbitrary set of per-stat constants:
- **Recompute-and-scale**, for stats where Hell already fully recomputes an absolute value from scratch: monster HP, damage (normal + special, min + max), monster experience, and the gold-value formula. Torment = Hell's full formula output x `GetTormentDifficultyMultiplier()`.
- **Bonus-and-scale**, for stats that are pure additive deltas layered onto an existing base: monster armor class bonus (+80 for Hell), to-hit/to-hit-special bonus (+120 for Hell), and the monster level offset (+30 for Hell, which also drives item level/quality and combat to-hit math for free since other systems already consume `Monster::level()`). Torment = the monster's normal base + (Hell's own bonus amount x multiplier).
- Monster resistance: Torment reuses Hell's `resistanceHell` table unchanged - no new table, matching how Nightmare and Hell already share the same base resistance table between them.

### Where the multiplier is stored and read

- New `Oracool.tormentDifficultyMultiplier` option (`options.h`/`options.cpp`), a custom `OptionEntryTormentMultiplier` class (not the generic `OptionEntryInt<T>`) storing the value as raw tenths (11-50) internally - the generic int-slider display would otherwise show "20" instead of "2.0". `GetListDescription` reformats to one decimal place; a new protected `OptionEntryIntBase::GetEntryValue(index)` accessor was added to the shared base class so this (and any future similarly-shaped option) can read a specific entry's raw value without duplicating the base class's own list bookkeeping.
- New free function `GetTormentDifficultyMultiplier()` (`options.h`, defined after `sgOptions`'s own declaration to avoid a forward-reference) is the single read point every scaling formula calls.
- New `Oracool.difficultyLevelGate` boolean option, default on.

### Numeric safety: uint8_t overflow

`Monster::minDamage`/`maxDamage`/`minDamageSpecial`/`maxDamageSpecial`/`armorClass` are all `uint8_t` (max 255). Hell's own formulas already fit comfortably within that for vanilla data, but scaling further by up to the slider's 5.0x maximum can genuinely exceed 255 for some monsters - every Torment-branch computation is explicitly clamped with `std::min(..., 255)` before the `uint8_t` assignment, rather than letting it silently wrap (which would make a *higher* multiplier setting unpredictably *weaker* for some monsters - the opposite of what the slider is supposed to do).

### The difficulty enum and every place a 4th value needed wiring

- `_difficulty` (`levels/gendung.h`) gained `DIFF_TORMENT` before `DIFF_LAST`, which now equals it.
- Every hardcoded "3-only" switch/array/bound found during research was extended or fixed, several of which were genuine latent bugs waiting for a 4th enum value to expose them, not things this feature introduced:

## OE-012: Stackable Consumables

- Status: Build-verified; not yet user-tested
- Scope: Single-player inventory and belt consumables, save format, store pricing
- Eligibility: Potions and elixirs (`_iMiscId` between `IMISC_USEFIRST` and `IMISC_USELAST`, exclusive), scrolls, `IMISC_BOOK`, Hellfire oils, and `IMISC_SPECELIX`. Excluded: anything `_iClass == ICLASS_QUEST`, `IMISC_ARENAPOT`, and Hellfire runes (not in scope for this version; no format change needed to add them later).
- Identity: Two consumables merge only if they share the same base item (`IDidx`) and the same identified state (`_iIdentified`). Nothing else varies per-instance for these item types in this engine.
- Stack limit: 99 per `Item`.
- Storage: The stack count lives in `Item::dwBuff` bits 1-7 (bit 0 remains `CF_HELLFIRE`), not a new field. `dwBuff` already round-trips wholesale through both the save format (`ItemPack.dwBuff`) and the network item-sync format (`TItem.dwBuff`) as an opaque 32-bit value, with only bit 0 ever inspected elsewhere — so this avoids growing `ItemPack` (which would hard-break every existing save file, since `pfile.cpp`'s `ReadHero` does a strict `sizeof()` check) and needs no new save-version infrastructure.
- Save-format bug found and fixed as a prerequisite: `UnPackItem` reset `dwBuff` to 0 via `RecreateItem`/`InitializeItem` and never restored it from the packed data, silently discarding any bits beyond `CF_HELLFIRE` on every load — unobservable before this feature since no other bit was used. Fixed by restoring bits 1-31 from the packed value while preserving `RecreateItem`'s freshly re-derived `CF_HELLFIRE` bit (which must not be overwritten by the saved value, since vanilla Hellfire saves don't reliably carry it and the engine intentionally re-derives it from the current session's Hellfire state instead of trusting the saved byte).
- Automatic merging: `AutoPlaceItemInBelt`/`AutoPlaceItemInInventory` run a merge pre-pass (mirroring the existing `AddGoldToInventory`/`GoldAutoPlace` "top off existing, then fall back to empty slot" pattern) before falling through to normal empty-slot placement. This covers ground pickup, auto-pickup, and every store purchase with no separate call sites, since they all funnel through these two functions. `NumMiscItemsInInv` (an existing Gameplay potion-pickup-cap helper, unrelated to Oracool) now sums stack quantities instead of counting item instances, so those caps keep working correctly once potions stack.
- Consumption: Using a stacked consumable (`UseInvItem`, `ConsumeScroll`) decrements the stack by one and only removes the slot when the count reaches zero, via new `DecrementOrRemoveInvItem`/`DecrementOrRemoveSpdBarItem`/`DecrementOrRemoveInventoryOrBeltItem` helpers. The existing `RemoveInventoryOrBeltItem` family is left untouched, since it's shared with non-stacking quest-item removal elsewhere.
- Succubus steal fix: `AddStealPotions` previously removed a belt slot outright (`IMISC_HEAL`/`IMISC_MANA`) or collapsed it via `InitializeItem` (`IMISC_FULLHEAL`/`FULLMANA`/`REJUV`/`FULLREJUV`), either of which would have destroyed an entire stack instead of stealing one unit. Fixed to decrement the source stack by one; the downgrade-tier case splits off exactly one unit into a scratch item and places it via the normal belt auto-placement (merge-or-empty-slot, best-effort — lost if there's no room, matching existing steal semantics).
- Manual drag/drop: `CheckInvPaste`'s inventory and belt paste branches gained a stack-merge case (same fill-then-remainder math as the pickup merge pre-pass) ahead of the existing swap logic.
- Splitting: Shift+right-click on a stack of more than one opens a split dialog reusing the existing gold-drop quantity-entry UI (`OpenGoldDrop`/`GoldDropInputState`/`DropGoldFlag` and all its existing guard wiring across the codebase), rather than building a parallel dialog system. `DrawGoldSplit` and `control_drop_gold` now branch on whether the source slot holds gold or a stackable consumable; a new `RemoveStackSplit` handles the consumable case (inventory or belt) and places the split-off amount on the cursor.
- Quantity display: Rendered in `DrawItem` (the single function used by the inventory grid, the belt, and the cursor-held sprite), bottom-right of the icon, avoiding the belt's existing top-right hotkey-number overlay.
- Store pricing: Griswold's and Adria's sell-list construction (`StartSmithSell`, `StartWitchSell`) multiplies the computed per-unit price by the stack quantity for stackable consumables. Selling always sells the whole stack in one transaction; no partial-sell dialog was added to the store screens.
- Save migration: Lazy — existing unstacked consumables on old saves are unaffected until the next matching pickup or purchase merges them naturally. No migration pass runs on load.
- Configuration: `Stackable Consumables=1` in `[Oracool Edition]`, alphabetized in the ITEMS AND PICKUP group; enabled by default. Disabling skips the merge pre-pass and drag-drop merge only — existing stacks remain intact and usable, matching the "preserve existing state, block new instances" pattern established by Remove Stat Limits.
- Verification: The complete Debug build succeeds. New coverage: `test/items_test.cpp` (stack-count clamping, eligibility, identity), `test/pack_test.cpp` (save round-trip including the `dwBuff` fix and a corrupt-data clamp case), `test/inv_test.cpp` (merge into existing/full/mismatched stacks, option-disabled fallback, stacked-scroll decrement-to-zero), `test/missiles_test.cpp` (Succubus steal only removes one unit, for both the direct-removal and downgrade-tier cases), `test/stores_test.cpp` (stack-aware sell pricing).
- Deferred: In-game manual acceptance has not yet been performed (merge/overflow-split, quantity overlay, splitting, stacked-scroll use-to-zero, store purchase/sale, loading a pre-feature save, Succubus steal against a large stack, disabling the option).

### Acceptance correction

- Initial user testing found that buying certain consumables (Health Potion, Full Mana Potion, Town Portal Scroll confirmed) while owning none of that item spent gold but placed nothing in the inventory or belt.
- Root cause: `Item::clear()` only resets `_itype` (the field `isEmpty()` checks) and deliberately leaves every other field — including `_iMiscId`, `_iClass`, and `IDidx` — as stale leftover data from whatever last occupied the slot, since vanilla code always fully overwrites a cleared slot via assignment rather than reading its other fields. `isStackableConsumable()` did not check `isEmpty()` first, so a cleared slot whose stale `_iMiscId` happened to match the item being purchased looked like a valid merge target. The merge pre-pass silently "absorbed" the purchase into a slot the engine still considers empty, so the real item was never actually placed anywhere.
- Fix: `isStackableConsumable()` now returns `false` immediately for an empty item, before inspecting any other field.
- Correction verification: A regression test reproducing the exact reported scenario (empty inventory/belt, buy Potion of Healing) now passes, alongside two new `Item`-level unit tests for the cleared-slot case, and all 247 automated tests pass.

## OE-013: Belt Mod

- Status: Build-verified; not yet user-tested
- Scope: Single-player belt slots, building on OE-012's stacking machinery
- Change: A belt slot now holds its own physical, capped stock (an `Item` with a stack count up to 99) rather than emptying after a single use. When a slot's stock is fully consumed, it automatically refills in one batch from a matching inventory stack (same `IDidx` and identified state), pulling from additional matching stacks in inventory scan order if the first one doesn't reach the cap. If nothing in inventory matches, the slot simply goes empty and is free for any item to occupy next — belt layout is never "reserved."
- Refill trigger: Refill happens once, when the slot's stock hits zero — not after every individual use. A belt slot behaves like a self-contained pile that occasionally reaches back into the bag for a fresh load, rather than syncing with inventory on every keypress.
- Implementation: `RefillBeltSlotFromInventory` (`inv.h`/`inv.cpp`) is called from `DecrementOrRemoveSpdBarItem` — the single choke point for real belt consumption (belt hotkeys, controller belt use, and scroll use via `ConsumeScroll` all funnel through it) — right after the slot is cleared, using the item's `IDidx`/identified state captured *before* clearing (per the OE-012 lesson: never trust a just-cleared slot's own fields). Drained inventory stacks are removed via `Player::RemoveInvItem`, which correctly compacts `InvGrid`/`_pNumInv` and handles its own network sync. Other removals from the belt — dragging an item off, splitting a stack, a Succubus steal, a store sale — call `RemoveSpdBarItem` directly and correctly do **not** trigger a refill, since none of those are "consumption."
- Legacy interaction: Vanilla's pre-existing `autoRefillBelt` Gameplay option redirects belt-item use to a matching inventory or belt item *before* consumption — a workaround that predates real stacking. It's bypassed whenever Belt Mod is active, so a belt slot's own physical stock is always what's actually consumed.
- Manual control: Dragging items onto/off belt slots and reordering the belt work exactly as before (OE-012's existing `CheckInvPaste` merge logic) — no changes needed.
- UI: An occupied belt slot no longer shows the vanilla hotkey-number overlay (the "1"-"8" that ordinarily appears top-right) while Belt Mod is active — the OE-012 stack-count overlay already conveys quantity, and the hotkey number was redundant clutter now that a slot can genuinely hold a running stock.
- No save-format change: this feature only moves existing `Item`s between `InvList` and `SpdList`, both of which already save correctly; no new `dwBuff` bits or `ItemPack` fields were needed.
- Configuration: `Belt Mod=1` in `[Oracool Edition]`, alphabetized directly after `Stackable Consumables`; enabled by default. Every code path is gated on single-player, `Stackable Consumables`, and `Belt Mod` together, since the feature is meaningless without stacking.
- Verification: The complete Debug build succeeds. New coverage in `test/inv_test.cpp`: last-unit consumption refills from a matching inventory stack (and removes the drained inventory slot), refill combines multiple matching inventory stacks up to the 99 cap, an identified-state mismatch is skipped, no matching stock leaves the slot empty, and disabling Belt Mod falls back to vanilla empty-on-last-use even with matching stock present.
- Deferred: In-game manual acceptance has not yet been performed (refill from a large inventory stack, depletion with no backup stock, hotkey-number suppression, drag/drop still working, pickup/purchase still topping off the belt first, disabling the option to confirm vanilla behavior returns).

## OE-016: Shared extended item-data and save foundation

- Status: Build-verified; enabling architecture only, no player-visible feature yet, acceptance explicitly deferred (roadmap document section 7)
- Scope: Data model and save-format groundwork for the future Rare (OE-008), Buffed Unique (OE-009), and Primal (OE-010) item tiers. No item generation, drop, pricing, or UI logic is introduced by this entry — those come in later roadmap items and build on top of what's added here.
- Data model: `Item` gains `OracoolItemTier _iOracoolTier` (`None`/`Rare`/`BuffedUnique`/`Primal`), `bool _iOracoolPerfectRoll`, and up to three prefix and three suffix `OracoolAffix` entries (`item_effect_type type`, `int32_t param1`, `int32_t param2` each) — the same shape as vanilla's existing single-prefix/single-suffix magic-item affix system (`_iPrePower`/`_iSufPower`/`_iVAdd*`/`_iVMult*`), generalized to hold up to six named affixes instead of two. `Item::hasOracoolTier()` is the safe accessor, guarded against `isEmpty()` for the same reason `isStackableConsumable()` needed the same guard after the OE-012 bug: `Item::clear()` only resets `_itype`, so a cleared slot's stale `_iOracoolTier` must never be trusted.
- Why this doesn't touch item power: a tiered item's actual resolved stat bonuses (`_iPL*` fields) already round-trip losslessly through the existing, unmodified `"heroitems"`/`"game"`/stash save streams, the same as any other magic item. The new tier/affix data is purely additional identity and display information layered on top (which named affixes contributed, and the tier label/color/popup detail) — losing it degrades an item back to looking and behaving like a plain heavily-rolled magic item, it never destroys the item or its power.
- Save format: A new, separately-versioned archive sub-file (`"heroitemsext"` for character saves, `"spstashitemsext"`/`"mpstashitemsext"` for the stash) carries only the tiered items' extension data, keyed by `Item::keyAttributesMatch()` (seed + base item + create info) rather than by array position. This deliberately avoids two fragile alternatives: growing `ItemPack`/`PlayerPack` (which `ReadHero` validates with a strict `sizeof()` equality check — any resize breaks loading of every existing save) or extending `LoadItemData`/`SaveItem`'s fixed positional layout (shared by `"heroitems"`, the `"game"` dropped-item stream, and the stash — a misread in any one desyncs the rest of that stream).
- Old-save compatibility: A save with no tiered items never gets a `"heroitemsext"` file at all (skipped on write), which reads back identically to a genuinely old, pre-feature save — every item simply keeps its default `OracoolItemTier::None`. No migration pass is needed since there is nothing to migrate.
- Corruption handling: The extension file carries its own 1-byte version (rejected gracefully if higher than this build supports) and a record-count sanity ceiling. Each record's affix counts are bounds-checked against `Item::MaxOracoolAffixesPerSlot` before trusting the stream's byte offsets; an individual out-of-range affix *type* is recovered in place (clamped to invalid) rather than aborting, since its byte width is fixed and known regardless of its value. Any record that fails validation stops the load there — records already applied stay applied, and the underlying items (already loaded via the unmodified vanilla-compatible paths) are never touched or destroyed.
- Compatibility: Every save/load call site is explicitly gated on single-player (`!gbIsMultiplayer`), keeping multiplayer entirely on the unmodified vanilla path. No existing save-format field changed size or layout.
- Verification: The complete Debug build succeeds. New coverage in `test/items_test.cpp` (`hasOracoolTier()` true/false/cleared-item regression) and new `test/loadsave_test.cpp` (full round trip of a fully-populated tiered item with all six affixes through a real character save/load cycle, an absent-extension-file old-save-compatibility case, a defensive-clamp case for an out-of-range in-memory affix count, and a stash round trip).
- Deferred: This phase has no player-facing feature to manually test (per the roadmap's own framing, "an enabling architecture phase rather than a visible item tier") — acceptance is explicitly deferred until Rare Items (OE-008) gives this foundation its first real, visible user.

### Acceptance correction

- On 2026-08-04, the user reported that a batch of Rare/Buffed Unique/Primal items left on the dungeon floor, then saved and reloaded, sometimes came back as plain magic items - name, stats, and durability intact, but tier coloring and affixes gone. Root cause: `SaveOracoolItemExtensions`/`LoadOracoolItemExtensions` (this entry's own save mechanism) only ever scanned player-carried containers - `InvBody`, `InvList`, `SpdList`, and the Tabbed Inventory's `InvTabList` (OE-017) - never the dungeon floor's own `Items`/`ActiveItems` arrays. `LoadItemData`/`SaveItem` (the vanilla-compatible positional save format this entry's own doc above explicitly avoided extending) round-trip a ground item's baked-in name, stats, and `_iMagical` directly and correctly, but they never touch the newer `_iOracoolTier`/affix fields - those simply reset to their zero-value defaults on every load unless something re-applies a matching extension record afterward, exactly as this entry's own "why this doesn't touch item power" note predicts for *any* container this mechanism doesn't cover. This wasn't a partial/random effect - every ground-dropped tiered item was unconditionally affected; "sometimes some" in the report most likely just reflects that the user didn't have a chance to check every single dropped item.
- Fixed by adding matching collect/apply coverage for the dungeon floor's dropped items: `CollectOracoolGroundItemExtensions`/`ApplyOracoolGroundItemExtRecord` (index-based over `ActiveItems`, since ground items aren't a contiguous array the way player-carried containers are) join the existing `"heroitemsext"` read/write pipeline. The write side is trivial (ground items are already live in memory whenever `SaveOracoolItemExtensions` runs). The read side needed its own call site, `ApplyOracoolGroundItemExtensions()`, invoked from `LoadGame` immediately after `LoadDroppedItems` repopulates `Items`/`ActiveItems` for the level - `LoadOracoolItemExtensions` itself runs far too early in the load sequence (before any level, and therefore any ground item, exists in memory) to be reused directly for this.
- Known remaining gap, not fixed this round: this only covers the dungeon floor the player is actually standing on at the moment of "Save Game" - a tiered item left on a *different* level, later revisited, isn't covered, since that level's dropped items round-trip through its own separate per-level save file (`SaveLevel`/`LoadLevel`), which has no equivalent extension hook yet. Flagging for a future pass if this turns out to matter in practice, since fixing it would mean threading a per-level companion sub-file through level-transition code rather than the character-save code path this fix touched.
- Correction verification: new `RoundTripsTieredItemLeftOnTheGround` and `GroundItemExtensionsIgnoreSlotsOutsideActiveItems` tests in `test/loadsave_test.cpp` reproduce the exact bug (tier data present before save, gone after a simulated `LoadDroppedItems`-style raw reload, restored after the new apply step) and confirm a slot outside the live `ActiveItems` range is never scanned or matched. All six directly-touched regression suites (165 tests) pass. Version bumped to 0.1.13.

## OE-017: Tabbed Inventory

- Status: Build-verified; not yet user-tested
- Scope: Single-player character backpack, adding 9 extra pages beyond the original inventory grid
- Change: 10 small tab buttons are drawn in the gap between the ring row and the 10x4 backpack grid, one aligned above each grid column. Clicking a tab switches which page's contents the grid displays. Tab 1 is the character's original backpack (`Player::InvList`/`InvGrid`/`_pNumInv`) and is completely untouched by this feature — every existing equip, quest-item-scan, auto-pickup, store, and multiplayer-sync code path keeps reading and writing it exactly as before, unaware tabs even exist. Tabs 2-10 are 9 new, independent 40-cell storage pages (`Player::InvTabList`/`InvTabGrid`/`_pNumInvTab`), each the same size and shape as the original backpack.
- Placement constraint: The ring slots and backpack grid can't be moved to make more room for the tab buttons — their visuals are baked into the game's original `inv.cel`/`inv_rog.cel`/`inv_sor.cel` background art (extracted from the user's own DIABDAT.MPQ at runtime, not files this project has or can edit). The tabs are therefore purely code-drawn text (numbers 1-10, no new art), fit into the existing ~16px gap above the grid, matching the precedent already set by the Reset Stats "R" button.
- Tab styling: The selected tab is gold (`UiFlags::ColorGold`) and drawn a few pixels larger (2px further left, right, and up) than the others; inactive tabs are a muted gray (`UiFlags::ColorUiSilver`).
- Interaction: Picking up and placing items in an extra tab reuses the exact same click-handling code as the original backpack (`CheckInvPaste`/`CheckInvCut`'s existing multi-cell-footprint, stacking, and swap logic), redirected through a small set of accessor functions (`GetActiveInvGridCell`/`GetActiveInvListItem`/`GetActiveNumInv`) that resolve to either the real InvGrid/InvList/_pNumInv (tab 1) or the selected `InvTabGrid`/`InvTabList`/`_pNumInvTab` entry (tabs 2-10) depending on which tab is displayed. This means every existing backpack behavior — multi-cell item placement, Stackable Consumables merging, swap-on-replace, shift-click auto-equip/auto-belt — works identically in an extra tab, with zero duplicated logic and zero risk of the two behaving differently over time.
- Restrictions: Extra tabs never accept gold (gold stays tracked through the normal `InvList`/`_pGold` path — mirroring how the existing Stash also handles gold as a separate running total rather than a grid item) or quest items (which must stay somewhere the existing quest-scanning code, which only ever looks at `InvList`, can still find them). Both are rejected outright when attempting to paste into an extra tab.
- No network sync for extra tabs: every write to an extra tab skips the normal `NetSendCmdChInvItem`/`NetSyncInvItem` calls, since the feature is single-player-only and no multiplayer packet format exists for a page the other side has no concept of.

## OE-018: v0.2.0 Foundations Pass

- Status: Build-verified (165 automated tests across 6 suites); acceptance pending the user's manual playthrough before release

### Save-format consolidation (headline change)

- Root cause of the entire v0.1.11-v0.1.13 bug-fixing streak: OE-016's item tier/affix data lived in a separate `"heroitemsext"`-style sidecar file, requiring every player-carried container (and, as v0.1.13 showed, the dungeon floor) to be manually wired into its own collect/apply scan - a pattern that's easy to get incompletely right once, let alone every time a new container is added.
- `_iOracoolTier`, `_iOracoolPerfectRoll`, `_iOracoolPrefixCount`/`_iOracoolSuffixCount`, and the prefix/suffix `OracoolAffix` arrays are now written and read directly inside `SaveItem`/`LoadItemData` (`loadsave.cpp`) - the one fixed-size positional item record already shared by `SaveHeroItems`/`LoadHeroItems` (backpack/belt/equipped), `SaveStash`/`LoadStash`, `SaveDroppedItems`/`LoadDroppedItems` (ground items, on *every* level, not just the current one - closing the v0.1.13 known gap as a side effect), and `SaveInventoryTabs`/`LoadInventoryTabs`. One change now covers every container automatically; there is no longer a second mechanism that can fall out of sync.
- The entire sidecar mechanism - `SaveOracoolItemExtensions`, `LoadOracoolItemExtensions`, `ApplyOracoolGroundItemExtensions`, `SaveOracoolStashItemExtensions`, `LoadOracoolStashItemExtensions`, and their supporting collect/apply/read/write helpers and the `OracoolItemExtRecord` struct - has been deleted outright, along with its 7 call sites.
- A new `OracoolItemFormatVersion` byte, checked in `SaveHeroItems`/`LoadHeroItems`, makes a pre-v0.2.0 save fail loudly and cleanly (a clear "incompatible version" message) rather than silently misreading a now-differently-sized item record. The Stash's existing size-validation check (`IsStashSizeValid`) already catches the same mismatch for free, since it already computes its expected byte count from the same per-item size constants. `"heroinvtabs"`'s own pre-existing version byte was bumped and its comparison tightened from "reject only if newer" to "reject if not an exact match," so an old-format tab file degrades the same safe way an unrecognized future one already did (tabs simply stay empty).
- `ItemPack`/`PlayerPack` (the compact format used only for the character-select list and multiplayer transfer) and `TItem`/network sync were deliberately left untouched - tiered items can never exist in multiplayer (`oracool::IsSinglePlayer()`-gated at generation), so there was nothing there to round-trip, and touching `PlayerPack`'s own `sizeof()`-equality gate is a separate, higher-blast-radius vanilla mechanism not worth destabilizing for zero gameplay benefit.

### Numeric-ceiling review

- The Gold Stacks Buff's cap (`GoldStackSaveLimit`, previously tied to `std::numeric_limits<uint16_t>::max()`, 65,535) was more conservative than it needed to be - tracing the actual save path showed single-player's authoritative item data was never actually constrained by that 16-bit figure, only a compact preview field that's irrelevant once the buff's own single-player gate applies. Raised to 100,000,000 (comfortably below any realistic overflow risk from `StoreGoldFit`'s per-cell multiplication, and far beyond anything a real playthrough would accumulate).
- Investigated whether the font-color palette could be genuinely expanded (the Primal-color comment previously claimed "no cyan font asset exists"). `UiFlags` was widened from a 32-bit to a 64-bit flags enum regardless - it had all 32 bits already assigned, so this removes the ceiling for any future color or flag, and the change is confirmed low-risk since `UiFlags` is never serialized to any save or network struct. However, inspecting the actual `.trn` remap files and the palette layout documented in `Source/engine/palette.h` showed the earlier comment was overly pessimistic in the wrong direction: font `.trn` assets are the project's own committed files, not copyrighted data read from the user's Diablo install, so authoring one isn't blocked by that - but the palette itself only has named bright-color blocks for blue, red, yellow, orange, beige, and gray. There is no green/cyan block to remap into without an actual palette edit, which is out of scope here (it would affect every other rendering path too). ## OE-021: v0.2.3 Fixed potions that silently refused to stack

- Status: Build-verified (172 automated tests: items_test 49, inv_test 40, stores_test 8, loadsave_test 8, player_test 4, pack_test 58, missiles_test 5)
- User-reported bug: "from time to time" a Health or Mana potion wouldn't stack with an otherwise-identical existing stack in the belt. Investigated by tracing `canStackWith` (`items.h`), which compared `IDidx` (the item's specific `_item_indexes` value).
- Root cause: `AllItemsList` (`itemdat.cpp`) carries **two separate `_item_indexes` entries** for several potions - a dedicated one used only by vendor stock and starting gear, and a different one that monster/floor drops actually use - both sharing the identical display name, icon, and `_iMiscId`, with no way for the player to visually tell them apart. Confirmed concretely: Pepin's Healing and Full Healing stock (`stores.cpp:242`, `SmithPepinPotionTypes`) hardcodes `IDI_HEAL`/`IDI_FULLHEAL` directly; Adria/the Witch's shop pins `IDI_MANA`/`IDI_FULLMANA` at fixed slots (`items.cpp:4693`, `SpawnWitch`'s `PinnedItemTypes`); and every new character's starting belt (`items.cpp:3420-3423`) uses `IDI_HEAL`/`IDI_MANA` directly too. All three bypass `ItemMiscIdIdx` (`objects.cpp:4458`), the lookup helper that deliberately skips `IDROP_NEVER` entries to find the regular drop-pool index - which is exactly why Pepin's Rejuvenation/Full Rejuvenation stock (looked up via `ItemMiscIdIdx`, not hardcoded) was never affected and the user never reported an issue with those two. This is a pre-existing vanilla Diablo/DevilutionX characteristic, not something Oracool introduced - it was invisible before Stackable Consumables (OE-012) gave `IDidx` equality any gameplay consequence.
- Fixed at the comparison, not the many producer call sites (which likely rely on the specific reserved indices for other reasons - fixed-slot vendor stock, `IsAnyOf(idx, IDI_MANA, IDI_FULLMANA, IDI_PORTAL)` checks elsewhere, etc. - not worth the risk of touching for a stacking-only bug). `Item::canStackWith` (`items.h`) now compares `_iMiscId` (the field that actually determines a potion/oil/book's kind, shared by both duplicate indices) plus `_iSpell` instead of `IDidx`. `_iSpell` is required alongside `_iMiscId` because every scroll spell shares the same generic `IMISC_SCROLL` - without it, a Scroll of Firebolt would incorrectly stack with a Scroll of Identify.
- New tests: `Item.CanStackWith_SameKindDifferentUnderlyingIDidxStillStacks` reproduces the exact bug (same `_iMiscId`, deliberately different `IDidx`, now stacks); `Item.CanStackWith_DifferentScrollSpellsDoNotStack` guards against the regression the `_iSpell` check exists to prevent.

## OE-024: v0.2.6 Broken items, Reset Stats rework, and three bug fixes

- Status: Build-verified (180 automated tests: items_test 50, inv_test 44, stores_test 10, loadsave_test 8, player_test 5, pack_test 58, missiles_test 5)

### Items at 0 durability go inactive instead of being destroyed

- New `Item::_iOracoolBroken` bool field (`items.h`), local-save-only (not synced to multiplayer/hero-export, matching the `_iOracoolTier` precedent) - persisted as one extra byte per item record in `loadsave.cpp`'s `SaveItem`/`LoadItemData`. `OracoolItemFormatVersion`/`OracoolInvTabsVersion` bumped 1->2 and `OracoolItemExtensionSaveSize` grown by 1 byte accordingly - **this breaks save compatibility for any character saved under v0.2.0 through v0.2.5**, the same "start fresh" tradeoff as the v0.2.0 Foundations Pass.
- New `BreakOrRemoveEquipment(Player&, inv_body_loc, bool hiPri)` helper (`inv.cpp`/`inv.h`): in single-player, sets `_iDurability = 0` and `_iOracoolBroken = true` on the equipped item instead of calling the existing `RemoveEquipment` (a hard delete with no trace); multiplayer still calls `RemoveEquipment` unchanged, since there's no packet format for a "broken but equipped" item. ### Reset Stats: only remove manually-spent points

- User request: Reset Stats resetting all the way to class base values also erased permanent quest/shrine stat bonuses, which use the same `ModifyPlrStr`/`Mag`/`Dex`/`Vit` functions as manual point-spending with no way to tell the two apart after the fact.

Confirmed via the `CMD_ADDSTR`/`CMD_ADDMAG`/`CMD_ADDDEX`/`CMD_ADDVIT` network commands that the manual button is the *only* caller reaching `msg.cpp`'s `OnAddStrength`/`OnAddMagic`/`OnAddDexterity`/`OnAddVitality` handlers - the one precise, distinguishable hook point for "the player spent this via the UI."

- `ResetPlayerStats` (`player.cpp`) rewritten: instead of `ModifyPlrStr(player, starting.baseStr - player._pBaseStr)` (reset to class base), it now calls `ModifyPlrStr(player, -player._pStatPtsSpentStr)` (and the Mag/Dex/Vit equivalents), zeroes the 4 counters, and adds their sum back to `_pStatPts`. ## OE-025: v0.2.7 Inventory sort button

- Status: Build-verified (184 automated tests: items_test 50, inv_test 48, stores_test 10, loadsave_test 8, player_test 5, pack_test 58, missiles_test 5). Built and tested overnight while the user was away from the keyboard - no manual in-game pass yet.

### Click handling

- New `CheckInventorySortButtonClick(Point)` (`inv.cpp`/`inv.h`): hit-tests the button rectangle, and if hit, calls `SortInventoryBySellValue` and returns `true`. Wired into `CheckInvItem` right after the existing tab-click check, gated on `MyPlayer->HoldItem.isEmpty()` - unlike switching tabs (safe to do while holding an item), running a full inventory repack while something is on the cursor would be confusing about where that held item ends up, so the button simply doesn't respond in that state.
- Matches the existing "act immediately on mouse-down" model already used for tab-switching in this same function (`CheckInvItem` is called directly from the mouse-down handler in `diablo.cpp`), rather than the press-then-release model the Reset Stats button uses on the character panel - no new state variable needed, and no confirmation dialog per the locked-in decision.

### Sort algorithm

- `SortInventoryBySellValue(Player&)` (`inv.cpp`/`inv.h`), single-player only:
  1. Repeatedly scans tab 1's `InvList` for the first item where `CanItemEnterExtraTab` returns `true` (i.e. not Gold, not `ICLASS_QUEST`), removes it via the existing `Player::RemoveInvItem`, and records it with its `GetItemSellValue`. Repeats until no more relocatable items remain in tab 1, then does the same for each of the 9 extra tabs via `RemoveExtraTabItem`. Gold and quest items are never removed - they're simply skipped by the scan every time it re-runs.
  2. `std::stable_sort`s the collected entries descending by sell value (stable, so equal-value items keep their original encounter order - tab 1 before tab 2, etc.).
  3. Re-inserts each entry in that order via the existing `AutoPlaceItemInInventorySlot` (tab 1, slots 0-39 in order) falling back to `AutoPlaceItemInExtraTabSlot` (tabs 2-10 in order) - a deterministic top-left-first-fit scan, unlike `AutoPlaceItemInInventory`'s scattered "feels natural for a single pickup" search order, since a sort needs predictable left-to-right, tab-by-tab packing instead.
  4. Finishes with `player.CalcScrolls()` and `CalcPlrInv(player, true)`, matching every other function that mutates `InvList`/`InvTabList` directly.
- Correctness subtlety worth recording: the repeated "re-scan for the first relocatable item" pattern in step 1 is deliberate, not just simpler code. `RemoveInvItem`/`RemoveExtraTabItem` compact their list by swapping the *current last* item into the vacated slot - if a pinned Gold/quest item happened to be sitting at a lower index than the item just removed, a naive descending-index removal loop could have that swap silently relocate the pinned item's *array* index without the caller's knowledge, and re-processing indices in the wrong order could then skip evaluating it entirely. Always removing "whichever relocatable item the scan finds first" (rather than trusting any particular index across multiple removals) sidesteps this. Separately: that same swap-compaction *does* still shuffle a pinned item's underlying `InvList`/`InvTabList` array slot when an unrelated item elsewhere is removed - but `RemoveInvItem`'s own bookkeeping always remaps the affected grid cell's encoded index to follow the data, so the pinned item's actual on-screen grid position never moves, only its backing array index might. Verified in `SortInventoryBySellValue_LeavesGoldAtItsGridPosition` by checking the grid cell, not the array index.
- New tests: `InvTest.SortInventoryBySellValue_OrdersRelocatableItemsDescending`, `InvTest.SortInventoryBySellValue_LeavesGoldAtItsGridPosition`, `InvTest.CheckInventorySortButtonClick_HitsButtonAndSorts`, `InvTest.CheckInventorySortButtonClick_MissesWhenOptionDisabled`.
- Not yet covered by an automated test: multi-tab overflow (an item spilling from tab 1 into tab 2 because tab 1 is full) - the existing `AutoPlaceItemInInventorySlot`/`AutoPlaceItemInExtraTabSlot` fit-check logic this relies on is already covered elsewhere (e.g. `TabbedInventory_AutoPlaceItemInExtraTabs_PlacesWhenTab1IsFull`), so this wasn't re-verified end-to-end through the sort path specifically. Worth a manual check: fill the backpack close to full with items of varying value, click sort, and confirm the cheapest ones end up correctly relocated into tab 2 rather than left behind or duplicated.

- Decisions locked in on 2026-08-05 (see `project_future_feature_ideas` memory), plus one decided live with the user before implementation: keep the Stash's gold pool shared across every character (unchanged from today - `StashStruct`/`GetStashSavePath` already have no per-save-slot key); sale proceeds also deposit to the Stash, not inventory; keep today's inventory-gold-first-then-Stash-fallback purchase logic (`TakePlrsMoney`/`TakeGold`) completely unchanged; and - the live decision - keep the now-largely-vestigial inventory-gold machinery (`MaxGold`, `AddGoldToInventory`, `RoomForGold`, `StripTopGold`) in place rather than deleting it, in case a future "withdraw gold to inventory for hand-carrying" feature wants it. That feature turns out to already exist: the Stash's `WithdrawGold`/`StartGoldWithdraw` (`qol/stash.cpp`) already let a player pull gold back into inventory on demand, and needed no changes at all.
- Research finding that shaped the whole implementation: **every gold-pickup entry point (manual ground pickup via `InvGetItem`, auto-pickup via `AutoGetItem`) already funnels through exactly one function, `GoldAutoPlace` (`inv.cpp`)** - so redirecting pickup to the Stash only required changing one place, not hunting down every pickup path individually.

### Core redirect

- `GoldAutoPlace(Player&, Item&)` (`inv.cpp`): in single-player, deposits into `Stash.gold` first (capped defensively at `INT_MAX`, matching the same overflow guard already used by `CheckStashPaste`/`AutoPlaceItemInStash`), falling back to the original `AddGoldToInventory` path only for whatever doesn't fit (in practice, never - `Stash.gold` would need to already be within a single pickup's value of `INT_MAX`, i.e. billions of gold). Multiplayer is completely untouched - the `oracool::IsSinglePlayer()` branch is skipped entirely, falling straight through to the original inventory-placement code, identical to before this change.
- `StoreSellItem()` (`stores.cpp`): the same redirect, single-player only, for the gold credited by a completed sale - falls back to the original `AddGoldToInventory` + `_pGold` bump for multiplayer or the same astronomically-unlikely overflow case.
- Neither `TakePlrsMoney`/`TakeGold`/`TotalPlayerGold`/`StoreGoldFit` (store *spending*) needed any change - `TotalPlayerGold()` already summed `_pGold + Stash.gold` with no SP/MP gate, and `TakePlrsMoney` already drained inventory gold first then fell back to `Stash.gold` unconditionally. This is why the locked-in "keep purchase logic unchanged" decision required literally zero code changes to honor.

### Fixed along the way: auto-pickup would have silently stopped once the inventory filled up

- `HasRoomForGold()` (`qol/autopickup.cpp`, anonymous-namespace) gates whether gold auto-pickup even attempts a pickup, by checking for an empty inventory cell or non-full gold pile in `MyPlayer->InvGrid`. Once gold no longer lands in inventory, that check would have become actively wrong for single-player - it would refuse to auto-pick-up gold as soon as the backpack filled with ordinary items, even though the Stash (capped at `INT_MAX`) obviously still has room. Fixed by short-circuiting to `Stash.gold < INT_MAX` for single-player before falling through to the original inventory-based check for multiplayer.
- Manual ground pickup (`InvGetItem`) has no equivalent pre-check gate - it always attempts `GoldAutoPlace` directly - so it was already correct with no change needed, once `GoldAutoPlace` itself was fixed.

### Display

- Character panel (`panels/charpanel.cpp`) "Gold" field previously showed only `InspectPlayer->_pGold` (a cache of "gold sitting in `InvList`", kept in sync by `CalculateGold`). Now adds `Stash.gold` on top for single-player, matching the exact `_pGold + Stash.gold` pattern the store screen's `TotalPlayerGold()` (`stores.cpp`) has used all along - so the char panel and every store screen now agree on what "your gold" means, where before the char panel only showed the inventory portion.

### Left deliberately unchanged

- `CalculateGold` (`inv.cpp`) still only sums `InvList` - it's the source of truth for `_pGold`, which now specifically means "gold sitting in inventory" (almost always zero for a post-upgrade single-player character, but still meaningful for legacy gold left over from before this update, or the display-formula fallback above).
- `RoomForGold` (`inv.cpp`), used by `StartGoldWithdraw` to cap how much can be pulled back into inventory at once, is correctly still inventory-space-based - that's exactly the constraint a withdraw-to-inventory action should respect, unlike pickup which no longer needs to care about inventory space at all.
- New tests: `InvTest.GoldAutoPlace_SinglePlayerGoesToStash` (replaces the old `InvTest.GoldAutoPlace`, which exercised the pre-change inventory-placement behavior for what is now the single-player path), `InvTest.GoldAutoPlace_MultiplayerStillUsesInventory` (preserves the old test's exact scenario and assertions, now explicitly scoped to confirm multiplayer is unaffected).
- Not covered by an automated test: `StoreSellItem`'s Stash-credit branch - the function has internal (anonymous-namespace) linkage and is only reachable through the multi-step sell-confirmation dialog flow (`stextshold`/`stextsel`/`ConfirmEnter`), which would need new test-exposure machinery to drive directly; the change itself is a small, mechanical mirror of the already-tested `GoldAutoPlace` redirect. Worth a manual check: sell any item to Griswold or the Witch and confirm the sale price lands in the Stash total, not a new gold pile in the backpack.

## OE-027: v0.2.9 Subtle autosave indicator

- Status: Build-verified (185 automated tests, unchanged from OE-026 - this feature is pure rendering/timing with no new test coverage, matching the precedent set for other visual-only changes like OE-022's Reset Stats icon).
- User request, clarified same day it was floated: keep **both** notification styles side by side rather than replacing one with the other. Both currently call the identical `InitDiabloMsg(EMSG_GAME_SAVED, 1000)` banner - the autosave call site in `oracool/auto_save.cpp`'s `ProcessAutoSave()`, and the manual "Save Game" call site in `gamemenu.cpp`. The user's split: the manual-save call site stays completely untouched; only the autosave one switches to a new indicator.
- New `oracool/save_indicator.h`/`.cpp`: `TriggerSaveIndicator()` (starts a `SDL_GetTicks()`-based timer) and `DrawSaveIndicator(const Surface&)` (renders while a cycle is active). `ProcessAutoSave()` now calls `TriggerSaveIndicator()` instead of `InitDiabloMsg` when `autoSaveNotification` is on - the option's meaning (whether autosaves notify at all) is unchanged, only what they show. `DrawSaveIndicator` is called once per frame from `scrollrt.cpp`'s in-game UI overlay pass, right alongside the existing `DrawDiabloMsg` call it replaces for this one call site.
- Rendering approach, and why it's a blink rather than a smooth fade: the engine's text drawing (`DrawString`) has no alpha/opacity parameter, and the only transparency primitives available (`ClxDrawBlended`'s fixed 50%, `DrawHalfTransparentRectTo`'s flat rectangle fill) don't support blending arbitrary already-rendered text at a smooth range of alpha levels without new lower-level rendering work. If this doesn't feel subtle/smooth enough once actually seen in-game, revisiting it with genuine alpha blending is a bigger follow-up, not a quick fix.
- Drawn at a fixed `{8, 8}` screen-absolute position (not panel-relative), top-left corner, using `UiFlags::FontSize12` (the smallest available font size) - deliberately small and out of the way of any panel UI.
- New source file registered in `Source/CMakeLists.txt`'s explicit file list (this project doesn't glob sources).
- Not visually verified - no tooling available in this environment to render/screenshot the running game, matching the same caveat already on record for the Reset Stats icon.

## OE-028: v0.2.10 Mini-map with TAB 3-state cycle

- Status: Build-verified (185 automated tests, unchanged from OE-027 - this is a rendering feature, no new pure-logic unit to isolate cleanly; the full existing suite passing is what confirms the automap refactor below is behavior-preserving).
- User request, refined the same day: an always-in-a-corner small map, built on top of the existing full-screen Automap rather than new map-rendering logic from scratch. Refined further: TAB should **cycle through three states** - no map, mini-map, full map - instead of the existing plain on/off toggle.

### Automap refactor: extracting a reusable rendering core

- `DrawAutomap(const Surface&)` (`automap.cpp`) computed its screen-space geometry (viewport center point, how many dungeon tiles fit across the screen) directly from the `gnScreenWidth`/`gnScreenHeight` globals and `GetMainPanel()`, with no parameter for a smaller target area - a genuine obstacle, since simply passing a smaller/clipped `Surface` wouldn't shrink or recenter the drawn content, only clip it (confirmed by tracing the geometry math before touching anything).
- Split into `DrawAutomapCore(const Surface &out, Point screenCenter, int cellsBasisWidth, bool applyPanelAvoidance)` - identical tile/player-rendering logic, but with the two previously-hardcoded globals now parameters, and the side-panel-avoidance adjustment (irrelevant for a small corner map) made conditional. `DrawAutomap` itself becomes a thin wrapper passing the exact original values (`gnScreenWidth`, screen-center from `GetMainPanel()`, `applyPanelAvoidance=true`) plus the trailing `DrawAutomapText` call it always had - **byte-for-byte equivalent to the pre-refactor behavior**, confirmed by direct before/after comparison of the extracted math, not just by the full regression suite passing (which doesn't exercise rendering pixel output at all, only compiles/links against the changed signatures).
- New `DrawMiniMap(const Surface&)` calls the same `DrawAutomapCore` with a small `130x130` target (`out.subregion(8, 8, 130, 130)`), a heavily reduced `AutoMapScale` (12, temporarily overriding the global and restoring it afterward - safe since rendering is single-threaded and synchronous), `applyPanelAvoidance=false`, and a screen-center of the subregion's own midpoint (`{65, 65}`, since `Surface::subregion` coordinates are relative to the subregion's own origin, not the real screen). Draws a `DrawHalfTransparentRectTo` dark backing first so the tile shapes read clearly over the live game view instead of blending into it.

### TAB 3-state cycle

- New `bool MiniMapActive` (`automap.h`/`.cpp`), mutually exclusive with the existing `AutomapActive` by construction.
- `DoAutoMap()` (`control.cpp`), the single choke point both the keyboard (`SDLK_TAB`) and gamepad bindings route through (confirmed via `diablo.cpp:1730-1737`/`2103-2108`), rewritten from a two-state toggle to: no map (`!AutomapActive && !MiniMapActive`) -> `MiniMapActive = true` -> (`MiniMapActive` true) `MiniMapActive = false; StartAutomap()` -> (`AutomapActive` true) `AutomapActive = false` -> back to no map.
- `scrollrt.cpp`'s render call site changed from `if (AutomapActive) DrawAutomap(...)` to an `if/else if` also covering `MiniMapActive`, so the two states are drawn mutually exclusively as intended.
- The two "Hide Info Screens" action handlers (`diablo.cpp:1796`/`2270`, which already force `AutomapActive = false`) now also force `MiniMapActive = false`, so that action fully closes either map state, not just the full one.

### Known limitations, deliberately not addressed in this pass

- **Not persisted across save/load.** `AutomapActive` is saved (`loadsave.cpp`'s fixed-layout `LoadGame`/`SaveGameData`); `MiniMapActive` is not - it resets to "no map" on load/rejoin, same as loading into a fresh session. Persisting it would mean repurposing more of that same fixed-format save function this project has touched before (see OE-024's Reset Stats fields), which felt like more risk than this cosmetic state's value justified for this pass.
- The mini-map's `130x130`/scale-`12`/`{8,8}` constants are a first reasonable guess, not something that could be tuned by eye without rendering tools available in this environment - **not visually verified at all**, unlike most other UI work this session which at least had the existing full map's known-good behavior to reason from analogically. Worth the closest manual look of everything shipped tonight: confirm the player arrow and nearby rooms are actually legible at this size/scale before treating the constants as final.
- No new Oracool option to disable the mini-map specifically (TAB cycling through it is the only control) - if the constant blink-through during exploration turns out to be annoying, an option to skip straight from no-map to full-map might be worth adding as a follow-up, but wasn't part of the locked-in design.

### v0.3.1 update: mini-map size increased

- User request after trying it in-game: `MiniMapSize` raised from `130x130` to `169x169` (30% larger). `MiniMapScreenPosition` (`{8, 8}`) and `MiniMapScale` (`12`) are unchanged, so this shows more of the surrounding area at the same zoom level rather than the same area rendered bigger.
- The screen-position/scale/legibility caveats above still apply and haven't been re-verified at the new size.

## OE-029: v0.3.0 Level cap raised to 99

- Status: Build-verified, full regression suite green (192 automated tests across items_test/inv_test/stores_test/loadsave_test/player_test/pack_test/missiles_test/writehero_test/format_int_test).
- User request, shipped in the same v0.3.0 release as OE-011 (Torment): "increasing the level cap to 99 as in diablo 2 ... torment should provide a lot of xp." Explicit follow-up decision: both Torment and this are "major always-on features" - no toggle for either, and save compatibility is explicitly secondary to clean, future-proof code for this pair of features.
- Always-on, and applies to both single-player and multiplayer - unlike every other Oracool feature, this wasn't scoped SP-only. Rationale: `MaxCharacterLevel`/`_pExperience`/`ExpLvlsTbl` are core engine constants with no natural per-mode branch point (unlike Torment, which is a distinct `_difficulty` enum value that simply never exists in MP); threading a new SP/MP conditional through the core leveling and network-sync code for a level-cap number felt like a worse trade than just raising the shared constant.

### The extended experience curve (levels 51-99)

- Levels 1-50 are **byte-for-byte the original vanilla `ExpLvlsTbl` values** - leveling pace up to 50 is completely unchanged.
- Levels 51-99: each level's total requirement is the previous level's plus a delta that itself grows geometrically - `delta(n) = 220,000,000 * 1.04^(n-1)` for `n` = levels-past-50 (1 at level 51, 49 at level 99), added cumulatively onto the level-50 baseline (1,310,707,109). This was chosen over two simpler alternatives after modeling both numerically:
  - Continuing vanilla's own ~1.2x-per-level *total* growth ratio (decaying toward ~1.03x by 99) compounds to a level-99 total in the hundreds of billions - mathematically fine (no overflow risk with the widened type below) but an unreasonably long grind relative to realistic Torment kill rates.
  - A pure polynomial-in-levels-past-50 curve (`base + C*(levels_past_50)^3`) is nearly flat for the first several levels past 50 (level 51 needs barely more than level 50), which reads as broken/anticlimactic even though it isn't.
  - The chosen geometric-delta model starts at a delta close to vanilla's own level 49->50 delta (continuity of feel right after 50) and decelerates smoothly, landing at ~33.4 billion total at level 99 (~25x the level-50 requirement) - level 51 requires a real, noticeable step up (+220M, ~17% more than level 50), and the last few levels before 99 are each a multi-billion-experience undertaking, matching the "legendary grind" character other ARPGs give their level cap.
  - Full computed table is in `Source/playerdat.cpp`; the formula and reasoning are documented there in the array's leading comment so a future retune doesn't have to reverse-engineer the numbers.
- Torment's existing experience bonus (OE-011: Hell's `4 * (exp + 1000)` formula, further scaled by the adjustable Torment Difficulty Multiplier, doubled again for uniques) is the intended engine for reaching the new higher levels in reasonable time - this wasn't changed by this feature, since it was already the single biggest experience multiplier in the game and already scales with the same slider the user controls for difficulty.

### uint64_t widening (the load-bearing change this feature required)

- Level 99's ~33.4 billion experience requirement exceeds `UINT32_MAX` (~4.29 billion), so every experience-carrying field had to widen from `uint32_t`/`uint16_t`-ish widths to `uint64_t`:
  - `Player::_pExperience`, `Player::_pNextExper` (`player.h`).
  - `ExpLvlsTbl` (`playerdat.hpp`/`.cpp`).
  - The save-format fields in `LoadPlayer`/`SavePlayer` (`loadsave.cpp`, `NextLE`/`WriteLE<uint64_t>` instead of `<uint32_t>`).
  - `PlayerPack::pExperience` and `PlayerNetPack::pExperience` (`pack.h`), and every `SDL_SwapLE32`->`SDL_SwapLE64` call site packing/unpacking them (`pack.cpp`).
  - This is a genuine save-format and network-packet-format break for existing characters and for interop with unpatched multiplayer peers - consistent with the user's explicit "save compatibility is secondary" call for this pair of features.
- Added a `FormatInteger(uint64_t)` overload (`utils/format_int.hpp`/`.cpp`) alongside the existing `FormatInteger(int)`, since experience values no longer fit in `int`. Also had to add a disambiguating `FormatInteger(uint32_t)` overload - `TotalPlayerGold()` (returns `uint32_t`) converts equally well to either the `int` or the new `uint64_t` overload, which is an ambiguous-call compile error without a matching exact overload.
- The character panel's Experience/Next Level fields (`panels/charpanel.cpp`) gained a third letter-spacing tier (`-1`, mirroring the existing pattern already used for large damage numbers) for the now-possible 11-digit values, on top of the existing two-tier spacing that was tuned for the old ~10-digit maximum.

### A latent bug this surfaced: `_iCreateInfo`'s 6-bit level field

- `_iCreateInfo` (`items.h`) packs an item's origin level into its low 6 bits (`CF_LEVEL = 63`), with every other bit already claimed by a distinct flag - there was no spare room to widen it, and every level value stored there was already safely below 63 **except** one: `SpawnBoy` (`items.cpp`) stores the player's raw, unhalved character level (`stores.cpp`'s `SpawnBoy(myPlayer._pLevel)`) - the only one of the five town-vendor spawn functions that doesn't halve or otherwise pre-clamp the level before storing it (Smith/Witch/Healer use `level/2`, Premium clamps to 30). Once characters can reach 64-99, this would have silently corrupted the stored flags (the overflow bits bleed into `CF_ONLYGOOD` and beyond) and, on the rare path that re-derives an item from its `_iCreateInfo`, silently regenerated the boy's item at a much lower effective level than the one it was actually created at.
  - Fixed by clamping only the *stored* value to `CF_LEVEL`'s max (`std::min(lvl, static_cast<int>(CF_LEVEL))`) while still generating the item's actual stats from the real, unclamped level - the boy's item still scales with your true level, only the level recorded in its metadata saturates at 63.
  - `items/validation.cpp`'s `IsTownItemValid` had a parallel latent issue: its boy-item check compared the (already 6-bit-masked) decoded level against `MaxCharacterLevel` directly, which is a no-op once `MaxCharacterLevel` exceeds the field's own 63-value ceiling (a masked value can never fail a `<= 99` check). Fixed by clamping the comparison threshold itself to `min(MaxCharacterLevel, CF_LEVEL)`. Net effect: this specific validation can no longer distinguish "plausible" from "implausible" boy-item levels once the character cap exceeds 63, since every representable value is now plausible by construction - a minor, unavoidable reduction in an already-cosmetic anti-tamper check, not a new exploit surface (the boy's item price/stat caps in `IsShopPriceValid` are unaffected and still enforced).

### Not covered by an automated test

- No new automated test exercises leveling all the way from 50 to 99 end-to-end (that would mean simulating tens of billions of experience gain, which isn't a meaningful thing to unit-test). Coverage that does exist: the widened save/pack round-trip (`writehero_test`'s golden-hash regression, `pack_test`'s `MaxCharacterLevel`-parameterized validation tests), and the `ExpLvlsTbl` values themselves are exercised indirectly by every existing level-1 test (`player_test`'s `CreatePlayer` still asserts `_pNextExper == 2000`, confirming level 1 is untouched).
- Manual verification still needed: reaching level 51+ in a real game and confirming the on-screen experience bar hover text (see below) and character panel both display sane numbers, and that a Torment grind session actually feels like meaningful progress toward the new cap.

## OE-030: v0.3.0 Experience bar hover shows per-level progress

- User request, made while reviewing OE-029: the experience bar's hover tooltip (`qol/xpbar.cpp`'s `CheckXPBarInfo`) previously showed three absolute values - lifetime experience, the next level's absolute threshold, and experience remaining - all of which become unreadably large once the level-99 curve is in play (levels in the 90s deal in multi-billion-experience numbers).
