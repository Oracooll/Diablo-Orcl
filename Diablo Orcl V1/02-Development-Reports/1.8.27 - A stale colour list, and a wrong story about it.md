# 1.8.27 - A stale colour list, and a wrong story about it

> **Correction, same day.** This report first claimed the assert dialog *was* the Ctrl+Click bug -
> that it blocked the click. The user corrected it: *"the gold COULD be hovered. It just didn't move
> when CTRL+Clicked on."* If hovering worked, no dialog stood between the cursor and the click, and
> that causal claim was unsupported. The fix below is still correct; the explanation of what it fixed
> was not. **The Ctrl+Click bug is open.**

## The defect that is real

```
Expression: (InfoStringLineColors.empty() || perLineColors) &&
"InfoString gained lines whose colours were never recorded - use SetPanelString/AddPanelString"
cursor_tooltip.cpp:169
```

Two facts that are each harmless and together are not:

1. **`ClearPanelStrings()` runs only inside `CheckPanelInfo()`** - the *main panel's* hover pass.
   `CheckCursMove` routes an inventory hover straight to `CheckInvHLight()` and returns
   (`cursor.cpp:972`), so nothing on that path ever drops the previous frame's per-line colours.
2. **The gold arm of `CheckInvHLight` bare-assigned `InfoString`**, while the item arm two lines
   above it used `SetPanelString` - which is what clears and re-records the colour list.

The result is a colour list that outlives the text it belonged to: several entries against a
`lineCount` of one. The assert exists precisely to catch that, and it caught it.

**What I do not know** is the exact sequence of hovers that produces it, which is why the "it fires
on every gold hover" story was wrong - if it did, the user could not have hovered gold at all. The
condition needs a *non-empty* colour list, so some orderings reach it and some do not, and I did not
work out which. That is an honest gap, not a resolved question.

## The fix, both halves

**Local**, and what the assert asked for: the two gold hovers now go through `SetPanelString` -
`CheckInvHLight` (`inv.cpp`) and `PrintItemDetails`' gold arm (`items.cpp`). They were the same slip
in the same shape, each sitting directly beside a sibling branch that already did it right. The
stash's `"Sort"` hover (`stash.cpp`) got the same treatment: same exposure, not yet reported.

**Structural**, and the reason it could happen at all: `ClearPanelStrings()` now runs at the top of
`CheckInvHLight`, beside the `ActiveTabItemHovered` / `pcursinvtabidx` / `pcursinvtabitem` resets
that already mark the start of that pass. `CheckPanelInfo` clears in exactly that position for
exactly this reason; the inventory pass simply never got its own.

## Still open: Ctrl+Click gold to stash

Unchanged from 1.8.25, and no closer. Reading the path end to end - `CheckInvItem`'s
`IsStashOpen && isCtrlHeld` branch, `TransferItemToStash`, `AutoPlaceItemInStash`'s gold branch,
`CheckInvHLight`'s tab-0 `pcursinvitem` encoding - every step still looks correct for gold in tab 1.
Ctrl+Click moves non-gold items, confirmed by the user.

The disabled repro `DISABLED_CtrlClickTransfersGoldStackFromBackpackToStash` faults inside
`AutoPlaceItemInStash` with no tooltip involved. Before this correction I wrote that off as probable
harness init; with the tooltip explanation gone, **it is the strongest lead there is** and deserves
to be chased properly rather than dismissed.

## What this cost, and why

I had one screenshot and turned it into a complete causal story without checking it against what the
user had actually described - they said the click did nothing, never that they could not hover. The
pattern is the same one as the 56px slot comment: something written down confidently once, and never
tested against the thing it claimed to explain.

Two rules that would each have caught it:

- **A click that "does nothing" is not evidence about the click handler** - but neither is it
  evidence for the first plausible blocker found. Both directions need checking.
- **An assert proves its own condition fired. It does not prove it fired in the case being
  investigated.** Those are different claims, and I merged them.
