# 1.8.27 - The gold that could not be hovered

The assert dialog the user caught **is** the Ctrl+Click bug from 1.8.25. One screenshot closed a
question two days of reading had not.

```
Expression: (InfoStringLineColors.empty() || perLineColors) &&
"InfoString gained lines whose colours were never recorded - use SetPanelString/AddPanelString"
cursor_tooltip.cpp:169
```

## The mechanism

Two facts that are each harmless and together are not:

1. **`ClearPanelStrings()` runs only inside `CheckPanelInfo()`** - the *main panel's* hover pass.
   `CheckCursMove` routes an inventory hover straight to `CheckInvHLight()` and returns
   (`cursor.cpp:972`), so nothing on that path ever drops the previous frame's per-line colours.
2. **The gold arm of `CheckInvHLight` bare-assigned `InfoString`**, while the item arm two lines
   above it used `SetPanelString` - which is what clears and re-records the colour list.

So: hover any coloured item (colours recorded, one per line), then hover gold (text replaced with
one line, colours untouched). `InfoStringLineColors.size()` is now several against a `lineCount` of
one, and `DrawCursorTooltip` asserts. In a Debug build that is a modal dialog, every frame the
cursor sits on the gold - which is why **the Ctrl+Click never landed: the click could not get past
the dialog.** Nothing was wrong with `TransferItemToStash` at all, and every reading of it was
correct, which is exactly why reading found nothing.

The assert's own message named the fix. It had been firing at whoever would look.

## The fix, both halves

**Local**, and what the assert asked for: the two gold hovers now go through `SetPanelString` -
`CheckInvHLight` (`inv.cpp`) and `PrintItemDetails`' gold arm (`items.cpp`). They were the same slip
in the same shape, each sitting directly beside a sibling branch that already did it right. The
stash's `"Sort"` hover (`stash.cpp`) got the same treatment: same exposure, not yet reported.

**Structural**, and the reason this could happen at all: `ClearPanelStrings()` now runs at the top of
`CheckInvHLight`, beside the `ActiveTabItemHovered` / `pcursinvtabidx` / `pcursinvtabitem` resets
that already mark the start of that pass. `CheckPanelInfo` clears in exactly that position for
exactly this reason; the inventory pass simply never got its own.

## What this says about the last two days

I reported the Ctrl+Click path as "every step looks correct for gold in tab 1" and I was right - the
fault was never in that path. It was in a hover that ran a frame earlier and blocked the input. **A
click that "does nothing" is not evidence about the click handler.** Worth remembering next to the
screenshot rule from 1.8.24: I asked for a datapoint about *non-gold items* when the datapoint that
mattered was the dialog on screen.

The disabled repro `DISABLED_CtrlClickTransfersGoldStackFromBackpackToStash` stays disabled - its
access violation is inside `AutoPlaceItemInStash` with no tooltip involved, so it is a separate
question about harness init, not this bug.
