# 1.8.28 - Three harness lies, and the real gold clue

## The gold hunt, and what my own test was doing

I bisected the Ctrl+Click-gold path into seven probes. **Every failure was my test harness, and each
one imitated the reported bug convincingly:**

| Probe | Symptom | Actual cause |
|---|---|---|
| `AutoPlaceItemInStash` on gold | passes | - |
| `TransferItemToStash` | access violation | no `SNetInitializeProvider`, so `RemoveInvItem`'s `NetSendCmdParam1` faulted |
| `CheckInvHLight` on gold | access violation | same |
| `CheckInvItem(ctrl=true)` | **gold did not move** | `InspectPlayer` never set in the fixture, so `IsInspectingPlayer()` was true and `CheckInvItem` refused at its first line |
| linking any of it | LNK2001 | `ItemInvSnds`, `pcursinvitem`, `IsStashOpen` not exported to tests |

That fourth row is the one worth remembering: **an uninitialised fixture reproduced the user's
symptom exactly - "Ctrl+Click does nothing" - for a reason that has no bearing on the game.** Had I
stopped there I would have "found" the bug twice in one week and been wrong both times.

With `InspectPlayer = MyPlayer` added to `InvTest::SetUp` and a net provider initialised, the entire
chain passes: hover gold -> `pcursinvitem` -> `CheckInvItem` -> `TransferItemToStash` ->
`AutoPlaceItemInStash` -> stash pool. That is now a permanent test,
`CtrlClickTransfersGoldStackFromBackpackToStash`, and `pcursinvitem` / `IsStashOpen` gained
`DVL_API_FOR_TEST` so it can exist.

**So the whole transfer chain is exonerated by test, not by reading.**

## The user's clue, which is the actual answer

> "the area where the hover and ctrl+click works is just very tiny. only a few px somewhere around
> the top part of the grid boxes."

That is not a gold bug at all - it is a **hit-rect geometry bug in the backpack**, and gold merely
made it visible because a gold stack is the thing you Ctrl+Click repeatedly until you notice. It also
explains why non-gold "worked": those clicks happened to land in the live strip.

`InvRect`'s backpack cells are built in `MakeInvRect` (`inv.cpp`) from `oracool::GridOrigin` and
`oracool::CellPx`, and hit-tested panel-relative in `CheckInvHLight`. The next step is to compare
that against where `DrawInv` actually paints the 10x7 grid, and to check the scan order: the loop
breaks at the FIRST containing rect and the thirteen equipment slots are scanned before the
backpack, so an oversized equipment rect overlapping the grid would leave exactly this signature - a
thin live band per cell with the rest claimed by a slot that then reports "empty".

**Not fixed in this build.** It is a different bug from the one I was chasing and deserves its own
measurement rather than another guess at the end of a long session.

## Levski's recipe book, third attempt

- **First**: fixed width 420, drawn off the left edge (title read "IPES").
- **Second**: flipped to the right when it did not fit - landing on top of the inventory.
- **Third**: clamped to x=0 - landing on top of Levski's own window and covering its title
  ("EVSKI'S" in the user's screenshot).

All three assumed the book's width and then argued about where to put it. It now takes the width it
can actually have: `clamp(window.x - SlotGap * 2, 220, 420)`, with the recipe text wrapped to that
width rather than to a constant. The book cannot overlap the window because it is never wider than
the gap beside it.
