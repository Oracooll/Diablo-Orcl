# 1.8.29 - The backpack grid is self-consistent, so it is not the grid

## What I claimed last build, and what the measurement says

I said the tiny live band was "a hit-rect geometry bug in the backpack" and named two suspects:
`MakeInvRect` disagreeing with where `DrawInv` paints, and the scan order letting an oversized
equipment rect claim the grid.

New test `EveryBackpackCellIsLiveAcrossItsWholeRect` walks **all 70 cells** and probes all **four
corners** of each cell's own rect, one pixel in. Every one resolves to that cell. So:

- `InvRect`, `CheckInvHLight` and `GetInventoryPanelRect` all agree.
- No equipment slot overlaps the grid.
- The draw uses the same `invPanel.position + GridOrigin + c * CellPx` the hit test does, so the
  painted cells and the hit rects are the same rectangles.

**Both of my suspects are eliminated by measurement.** The backpack's own geometry is not the bug.

## What that leaves

The only remaining seam is between the **mouse position** and the space those rectangles live in.
The user is running **1024x768** (measurable from the screenshot's aspect and panel proportions),
not the 720-tall screen most of this project's hardcoded constants assume - `SidePanelContentBottom`
is literally `720 - 96`, and `GridOrigin.y` is anchored to a hardcoded 624.

That is a hypothesis, not a finding, and it is the third one this bug has produced. It gets measured
before it gets fixed.

**Two cheap datapoints would settle it**, and both are things only the user can see:

1. **Does the same tiny-band behaviour happen in the STASH grid?** The stash uses the same geometry
   idiom but a different origin and a 10x16 page. If the stash is fine, the fault is inventory-local
   and the resolution theory is wrong. If both are broken, it is shared - mouse space or a
   screen-height constant.
2. **Does it change at a different resolution?** If the live band moves or disappears at 1280x720,
   the 720-tall assumptions are the cause and there is a list of them to sweep.
